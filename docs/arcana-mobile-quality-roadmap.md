# 모바일 게임 완성도 로드맵

기준: 2026-11-01, Asia/Seoul. 사용자의 목표는 독립 모바일 게임 수준의 완성도다. 현재 결과물은 웹 게임이며 앱 패키징, 스토어 출시, 실기기 성능을 완료했다고 간주하지 않는다. 오락성 → 그래픽 → 최소 교육 순서를 유지한다.

## 참고작에서 가져올 기준

| 참고작 | 적용할 설계 기준 | 아르카나에서 확인할 결과 |
| --- | --- | --- |
| 클래시 오브 클랜 | 거점의 성장과 시설·유닛의 명확한 실루엣 | 준비 아트와 실제 업그레이드 모델이 연결되고 단계 차이가 작은 화면에서도 보임 |
| 브롤스타즈 | 빠른 입력 반응, 공격 예고와 역할 가독성 | 이동·대시·필살기를 손가락으로 구분하고 위험과 명중 시점을 읽을 수 있음 |
| 킹샷 | 구조 요청·지역 확장·거점 성장의 연결 | 다음 목적지, 구할 대상, 해금 이유와 보상이 명확함 |
| 탕탕특공대 | 다수의 적 속 가독성, 짧은 강화 선택 리듬 | 적·공격·보상이 겹쳐도 우선순위가 읽히고 성장 선택이 다음 전투에 반영됨 |
| 아빠와 나 | 준비·접촉·회복 동작과 타격 반응 | 망치·검·마법마다 공격 무게와 넉백 반응을 구분할 수 있음 |

위 표는 참고할 방향이며 해당 게임을 직접 측정한 성능 비교가 아니다. 고유 캐릭터·미술·브랜드·화면·과금 구조를 복제하지 않는다. 구체적인 비교를 보고할 때는 실제 참고 화면이나 플레이 근거를 남긴다.

## 시간별 순환과 산출물

매 회차 모든 분야를 짧게 점검하되 **하나의 완료 가능한 개선**을 선택한다. 이전 summary의 `next_lane`을 이어서 진행하며 완료 시 다음 순서로 넘어간다. 시작 기록에는 `primary_lane`, 수용 기준, 담당 파일, 검증 계획을 쓴다. 최종 기록에는 `next_lane`, 분야별 상태(확인·가설·미측정), 결과, 다음 후보를 남긴다. 첫 회차는 기획부터 시작하며 실제 모바일 병목에 근거해 작은 구현을 고른다.

| 순서 | 분야 | 완료 단위 예시 | 검증 |
| --- | --- | --- | --- |
| 1 | 기획 | 다음 원정 목표·선택 이유가 드러나는 작은 흐름 개선 | 실제 진입→선택→출발, 막힘·중복 안내 확인 |
| 2 | 게임성 | 공격 리듬·난이도·보상 선택 한 가지 개선 | 수정 전후 동일 시나리오, 실제 패배/성공 경로, 재미는 검증 가설로 구분 |
| 3 | 디자인 | 준비 아트·전투 HUD·성장 화면 한 흐름 개선 | PC/모바일 이미지, 터치·키보드·대체 표시 |
| 4 | 모델링 | 캐릭터·몬스터·타워·거점 중 한 에셋 또는 모션 | 편집 원본·재생성·접지·크롭·실제 전투 화면 |
| 5 | 구조/로직 | 입력·일시정지·저장·보상·렌더 비용의 확인된 문제 해결 | 실제 반례와 의미 있는 회귀 검사, 저장 호환성 |
| 6 | 모바일 | 화면 비율·한 손 조작·회전·복귀·로딩 병목 하나 해결 | 세로/가로, 안전 영역, 터치, 백그라운드 복귀 |

확인된 오류와 소유권이 명확한 미완료 작업은 순서보다 우선한다. 매시간 여섯 분야를 모두 대규모 수정하지 않는다. 기획 문서만 쌓거나 작은 문구 변경만 반복하지 말고, 안전하게 구현 가능한 실험으로 연결한다. 개선 근거가 없으면 억지 변경 없이 기록한다.

## 모바일 수용 기준과 우선 후보

- 준비 화면은 컨셉 아트 중심, 스테이지 진입 후 전투 전용 화면. 최종 모델의 색·재질·실루엣은 아트를 참고하지만 경로·충돌 판정은 엔진 데이터를 따른다.
- 우선 후보는 모바일 세로 전장의 과도한 빈 공간, 조작 버튼과 전장 비율, 영웅/몬스터의 역할 실루엣, 공격 예고와 접촉 반응이다. 현재 버전 화면에서 재확인 후 범위를 정한다.
- 390×844 세로와 844×390 가로를 기본 검증하고, 레이아웃 변경은 360px 폭도 확인한다. 주요 터치 목표는 최소44CSSpx를 목표로 하며 누르기 어려운 간격·도크 가림·가로 넘침을 확인한다.
- 화면 회전, 안전 영역, 일시정지·백그라운드 복귀, 모션 줄이기, 이미지 실패, 저장 복원은 영향을 받는 변경에서 확인한다.
- 목표는 대표 실기기에서 안정적인60fps이며 기기·장면별 측정 전에는 달성했다고 쓰지 않는다. 필요하면30fps 품질 선택을 검토한다. 소프트웨어 Chromium 결과를 실기기 FPS로 보고하지 않는다. 에셋 용량·드로콜 감소도 실측 성능과 구분한다.
- 기본 진행·보상·난이도는 실제 플레이로 검증한다. 자동 테스트 통과만으로 재미나 상용 게임 수준을 달성했다고 쓰지 않는다.

## Claude API 운영

관리 환경의 인증·프록시·TLS를 그대로 사용한다. KR2는 Sonnet5.5 구현 리드와 Haiku5.5/Opus5.5 역할 위임에, KRVIDEO는 지원되는 직접 이미지 검토에 사용한다. KR1 등 다른 키가 있다는 이유만으로 실패 시 조용히 바꾸지 않는다. 키 값은 문서·로그·저장소에 남기지 않는다.

Haiku5.5는 짧은 기획·설명 점검, Sonnet5.5는 기획 구체화·디자인·모델링·개발과 시각 검토, Opus5.5는 구조·좌표·애니메이션·전투·저장·보상 로직과 최종 독립 검토를 맡는다. 구현자가 아닌 역할의 최종 검토를 확보하고 실제 검증 자료를 제공한다. API 호출은 필요한 작업에 사용하며 사용 실적을 위한 호출은 하지 않는다. 입력 파일 해시·응답 모델·사용량과 검증 한계를 기록한다.
