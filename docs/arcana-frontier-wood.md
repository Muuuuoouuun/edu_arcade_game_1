# 변경 전장 통나무 병사의 보행과 접지

2026-11-09 KST · 컨셉 개발 58회차. 기준 `4ee0f3cc6d71ac3d7c10ad67221f28c192806ecc`, 소유 브랜치 `codex/arcana-stage-experience-20261106`.

## 선택과 구현

`docs/arcana-direction-loop/model-drafts/wood-log-compare-cycle34.webp`의 통나무·가지·잎 실루엣, 현재 `wood-soldier.png`의 초록 눈·몽둥이, 실제 변경 전장 PC/가로 모바일 화면을 비교했다. 기존 2.5D의 서리늑대 체형·영웅 방향 동작과 직전 회차의 3D 포탑 조준은 완료되어 있다. 이번 차이는 **3D 전장의 적이 여전히 단순한 사람 모형이며, 발을 움직이지 않고 이동하고 영웅 쪽을 향한다**는 점이었다.

- 기존 통나무 병사의 몸과 몽둥이, 1초 8관절 보행을 실제 3D 전장에 연결했다. 진행 방향으로 몸을 돌리고, 이동한 1.5 전장 단위마다 한 주기를 재생한다. 개체마다 이동 거리가 있어 일렬로 동시에 같은 발을 들지 않는다. 이동하지 않은 시간에는 걸음이 계속 진행되지 않는다.
- 정지하면 현재 걸음에서 0.16초 동안 원본의 두 발 지지 자세로 보간한다. 각 다리는 경사면·다리 표면에 맞게 높이를 조정하되 원본의 발 들기 높이를 유지한다. 애니메이션의 이전 원본 표본을 복원한 뒤 보정하여, 같은 시점의 반복 렌더나 일시정지에서 변환이 누적되지 않는다.
- 발목 기울기·무릎 굽힘의 전체 IK, 수평 월드 좌표에 발을 고정하는 기능은 아니다. 경사면에서는 발바닥의 높은 쪽을 지지하며 반대쪽이 조금 떠 있을 수 있다. 보폭 1.5는 게임 속도에서 읽히는 주기 설정이며 모든 프레임의 수평 미끄러짐 제거를 보장하지 않는다.
- 발밑 접촉 표시와 다친 적의 체력 막대도 같은 장면에서 묶어 렌더한다. 체력 막대는 지형/물체의 깊이 검사를 받는다. 최대 체력은 생성 시 기록한다.
- 피해·공격 시점·스킬·경로·보상·승패 규칙은 그대로다. **새 몽둥이 공격 클립을 제작한 것은 아니다.** 성문 공격/영웅 추격의 판정은 기존 엔진을 쓰며, 정지 시 보행에서 지지 자세로 돌아간다. 기존 2.5D 캠페인과 저장에는 변경이 없다.

## 모델과 렌더 구조

편집 원본 `wood-soldier.blend`를 읽어 파생 원본 `frontier-wood.blend`에 현재의 100개 편집 메시와 8개 움직이는 관절을 보존했다. 이전 문서의 메시 수 대신 이번 파일을 다시 열어 확인한 개수를 기록한다. 새 종을 모델링한 것으로 표시하지 않는다.

| 산출물 | 경로 / 규격 |
| --- | --- |
| 편집 원본 | `art-source/defense/frontier-wood.blend` · 100메시, 손목에 연결된 몽둥이, 1~33프레임 |
| 공통 카메라 렌더 | `art-source/defense/frontier-wood/walk-{0,1,2,3}.png` · 384×384, 원본 프레임 1/9/17/25 |
| 작업실 GLB | `public/defense/models/frontier-wood.glb` · 8메시, 4,026삼각형 |

전장용은 작은 화면에서 보이지 않는 내부 나이테 고리 일부를 생략하고 표면을 단순화한다. 접지 손상이 검출된 다리는 추가 축약에서 제외했다. 원본과 작업실 모델에는 나이테를 유지한다. 정점 색으로 목재와 초록 잎/눈을 구분하며 원본의 작은 발광 재질은 단일 재질에서 단순화된다. 두 GLB 모두 실제 지오메트리·관절 애니메이션이다. WebP를 3D 모델로 사용하지 않는다.

유닛별 WebGL 렌더러를 만들지 않는다. 개체의 8관절 변환만 따로 평가하고, 같은 관절 표면을 `InstancedMesh` 8개로 그린다. 접촉 표시와 체력 표시 각 1개를 더한다. 인스턴스 용량은 16부터 필요에 따라 두 배로 늘고, 사망 개체의 애니메이션 상태는 제거한다. 같은 지오메트리/재질을 공유하며 카메라 밖 개체는 그리기에서 제외한다. 모델 실패 시 기존 조작·전투를 유지하는 단순 입체 병사 묶음으로 대체한다.

```bash
npm run models:frontier-wood
npm run models:frontier-wood:check
node --experimental-strip-types --test src/games/frontier/woodView.test.ts
npm test
npm run build
```

생성기는 Blender 4.3.2 / Cycles CPU 24샘플, 투명 배경, 공통 정사영 카메라, ffmpeg WebP를 사용한다. 작업실에는 기존 통나무 병사 항목을 보존하고 전장용 제작 항목을 추가했다. 다른 캐릭터·포탑·성문·지형 파일을 덮어쓰지 않는다.

저장소 밖 `/tmp/arcana-hourly-20261109-0236/summary.md`에 시작 기준·범위·미완료 상태부터 기록한다. 아래는 이 범위에서 완료한 검증과 남은 한계다.

- 실제 Android/iOS GPU·발열·장시간 메모리와 사용자 재미 평가는 미완료다. 지형 완성, 전체 캠페인의 3D 이전, 분대원 정식 모델, 새 적 공격 동작을 완료로 표시하지 않는다.

### 실제 화면과 회귀

- 최종 모델의 PC 1440×900 및 터치 844×390에서 모드 진입·훈련 시작, 실제 이동 거리와 진행 방향, 2배속 거리 비율, 일시정지 중 캔버스 PNG 해시 일치, 동작 줄이기, 한 캔버스·화면 넘침 없음·페이지 오류 없음을 검사했다. 같은 10초 전장 상태의 전후 화면을 확인했다.
- 전장 GLB를 차단한 실제 솔로 화면에서 기본 입체 병사로 시작·공격·기술 조작이 가능했다. 작업실의 새 항목은 PC/모바일 로드·보행·와이어·자동 회전·시점 초기화·동작 줄이기와 PNG 대체를 확인했다. GLB와 PNG가 모두 실패했을 때의 안내와 재선택 복구도 검사했다.
- 실제 WebGL 검사 장면에서 몸과 체력 막대 표본은 가림 물체를 추가하기 전 각각 목재색/체력색, 추가 후 모두 앞쪽 빨간 물체의 픽셀로 바뀌었다. 깊이 검사 속성만 읽은 검사가 아니다.
- 최종 TypeScript/Vite 빌드 통과. 전체 **369개 중 368개 통과**, 기존 수학 `(3×7)/5`의 실제 4 / 기대 4.2 실패 1개. 새로운 전장·모델 테스트 5개는 통과했다. 기존 수학 소스와 해당 테스트는 변경하지 않았다.

### 비용과 남은 성능 한계

Chromium의 **SwiftShader 소프트웨어 GPU**, 가로 844×390에서 높이 242px인 동일 전장, 준비 상태에서 1/10/30마리의 위치·체력·카메라를 고정하고 걸음만 진행했다. 워밍업 2초 후 4초씩 측정했다. 기준은 `4ee0f3c`의 초기 모형이며, 모든 실행은 단일 캔버스다.

처음 4,026삼각형 모델을 그대로 사용했을 때 30마리 평균 프레임이 약 167ms였다. 최종 1,024삼각형 모델은 약 93~98ms로 줄었다. 기준의 약 63ms보다 잔여 비용이 있으므로 속도 향상이나 모바일 성능 합격으로 보고하지 않는다. 실제 기기 GPU와 더 긴 표본 검사가 필요하다.

| 적 수 | 기준 draw calls → 최종 | 기준 삼각형 → 최종 | 기준 GPU geometry 객체 → 최종 |

| 1 | 35 → 38 | 34,700 → 35,602 | 197 → 204 |
| 10 | 98 → 38 | 36,014 → 45,034 | 251 → 204 |
| 30 | 238 → 38 | 38,934 → 65,994 | 371 → 204 |

동일한 형태를 단순한 상자와 같은 비용으로 그린다는 뜻은 아니다. 표면 묶음과 지오메트리 공유로 개체 수에 따른 호출·객체 복제를 줄였으며, 최종 30마리 시험은 약 10fps인 소프트웨어 렌더링 스트레스 장면이다. 실제 웨이브와 실기기에서 렌더 해상도·그림자·군중 예산을 별도로 정해야 한다.

이번 회차에는 Claude API를 호출하지 않았다. 원격 main `8b54d75`와 Claude `35aaea7`/`bf7c1c6`는 시작 이후 새로운 변경이 없었다. 예약 도구 조회에서는 루프가 활성 상태이며 마지막 실행 시각이 `2026-11-08T17:36:18Z`로 반환되었다. 다음 시각과 완료 실행 기록은 비어 있었으며, 예약을 변경하거나 미래 실행 성공을 보증하지 않는다. 개발 커밋·푸시 성공은 별도로 확인한다.
