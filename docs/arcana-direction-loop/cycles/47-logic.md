## 2. 화면은 실제로 몇 번 그려지나

`DefenseGame.tsx`의 루프는 매 프레임 엔진을 1/60초씩 돌린다. 하지만 React 상태 게시는 `shouldPublishDefenseFrame`이 **32ms 이상 지났을 때만** 한다.
- 60Hz 기기는 두 프레임마다, 120Hz는 네 프레임마다, 30Hz는 매 프레임 게시한다.
- 그래서 전투판은 **기기와 상관없이 약 30Hz**로 그려진다.
- 단계 전환과 결과 화면 효과 종료는 예외로 바로 게시한다.

공격 포즈 구간(`attackPhase`: 준비 `hitAt`, 타격 0.12초, 회복 나머지)이 게시되는 장 수는 길이 ÷ (33.3ms × 배속)이다.

| 영웅 | 준비 / 타격 / 회복 (초) | 1배속 장 수 | 2배속 장 수 |
| --- | --- | --- | --- |
| 리엘 | 0.10 / 0.12 / 0.06 | 3.0 / 3.6 / 1.8 | 1.5 / 1.8 / **0.9** |
| 이안·청운·루나 | 0.15 / 0.12 / 0.06 | 4.5 / 3.6 / 1.8 | 2.3 / 1.8 / **0.9** |
| 브론 | 0.24 / 0.12 / 0.16 | 7.2 / 3.6 / 4.8 | 3.6 / 1.8 / 2.4 |
| 카르 | 0.28 / 0.12 / 0.16 | 8.4 / 3.6 / 4.8 | 4.2 / 1.8 / 2.4 |

**읽은 것**
- 2배속에서 원거리 영웅의 회복 포즈는 공격 10번 중 1번꼴로 **한 장도 그려지지 않는다**(0.06초 < 66.7ms).
- 타격 포즈는 2배속에서 1~2장이다.
- 그래서 원거리 영웅의 포즈 투자는 **준비·타격**이 먼저다(46회차 이안 초안의 측정과 같은 결론).

## 3. 히트스톱이 화면에 보이는 길이

41·43회차의 3단계 멈춤(50ms, 보스 90ms)을 위 루프 그대로 시뮬레이션했다. 프레임마다 1/60 단계를 돌리고, 경과 시간 상한은 0.1초, 배속을 곱하고, 32ms 게시 제한을 둔다. 사건 시각과 프레임 위상은 무작위이고, 조건마다 2만 번 돌렸다.

멈춤을 넣는 세 방식을 비교했다.
- **A 프레임만 건너뜀**: 시간은 계속 쌓는다. 43회차가 피하라고 한 방식이다.
- **B 43회차 원칙**: 사건이 있었던 프레임 다음부터 멈추고, 멈춘 동안 시간을 쌓지 않는다.
- **C B + 사건 단계에서 끊기 + 즉시 게시**: 단계 반복을 사건이 난 단계에서 멈추고, 못 돌린 단계는 버리며, 그 상태를 바로 게시한다.

‘유지’는 사건 상태가 처음 그려진 뒤 다음 그림까지의 시간이다. 평소에는 33ms다. ‘늦음’은 멈춘 그림이 사건보다 엔진 시간으로 얼마나 뒤인지다. ‘몰아치기’는 멈춤이 끝난 프레임에 한꺼번에 돈 단계 수다.

| 기기·배속 | 멈춤 | A 유지 / 몰아치기 | B 유지 / 늦음 최대 | C 유지 / 늦음 |
| --- | --- | --- | --- | --- |
| 60Hz 1배 | 50ms | 33~67 / **4단계** | 50~67 / 0 | **67** / 0 |
| 60Hz 1배 | 90ms | 83~100 / 6 | 100~117 / 0 | **117** / 0 |
| 60Hz 2배 | 50ms | 33~67 / **8** | 50~67 / 17ms | 50~67 / 0 |
| 60Hz 2배 | 90ms | 83~100 / 12 | 83~100 / 17ms | **100** / 0 |
| 30Hz 1배 | 50ms | 67 / 4 | 67 / 17ms | **67** / 0 |
| 30Hz 2배 | 50ms | 67 / 8 | 67 / **50ms** | **67** / 0 |
| 30Hz 2배 | 90ms | 100 / 12 | 100 / 50ms | **100** / 0 |

**읽은 것**
- **A는 몰아치기가 생긴다.** 멈춘 뒤 한 프레임에 4~12단계(67~200ms 분량)가 한꺼번에 돌아서, 적이 툭 튄다. 43회차 판단과 같다.
- **B는 몰아치기는 없다.** 하지만 두 가지 흔들림이 있다.
  - 게시 제한 때문에 사건 상태가 늦게 그려질 수 있어서, 유지가 50~67ms로 흔들린다.
  - 한 프레임에 여러 단계가 도는 2배속·저사양(30Hz)에서는 멈춘 그림이 사건보다 최대 50ms 뒤다. 숫자가 이미 떠오르고 불덩이가 사라진 뒤에 멈춘다.
  - 안드로이드 설치판 우선(사용자 결정)이라 저사양 기기 비중이 크다.
- **C는 늦음이 늘 0이다.** 50ms 멈춤은 67ms, 90ms 멈춤은 100~117ms로 거의 일정하게 보인다. 평소 33ms의 두 배다.
- 41회차 값(50·90ms)은 60fps 그림을 전제했다. 30Hz 게시에서는 평소 그림보다 한 장 더 머무는 정도다.
  - 값은 그대로 둔다. C 방식이면 이 ‘두 배 길이 한 장’이 매번 같은 순간(맞은 순간)에 걸린다.

## 4. 시계 함수 초안과 불변식

43회차가 제안한 순수 함수를 초안으로 썼다. 엔진은 건드리지 않는다.

```ts
export type BattleClock = { accumulated:number; last:number; stopUntil:number }; // 초 단위
/** 고정 단계 시계. 멈춤 동안은 시간이 쌓이지 않고 단계도 돌지 않는다. */
export function advanceClock(c:BattleClock, now:number, speed:number, step=1/60, cap=.1) {
  const elapsed = now <= c.stopUntil ? 0 : Math.min(cap, Math.max(0, now - Math.max(c.last, c.stopUntil)));
  let accumulated = c.accumulated + elapsed * speed, steps = 0;
  if (now > c.stopUntil) while (accumulated >= step) { accumulated -= step; steps++; }
  return { clock: { ...c, accumulated, last: now }, steps };
}
/** 단계 i에서 큰 순간이 났을 때: 남은 단계는 버린다(엔진은 같은 단계를 실제 시간으로 조금 늦게 돌 뿐). */
export const stopAt = (c:BattleClock, now:number, length:number):BattleClock => ({ ...c, stopUntil: now + length });
```

루프는 `steps`번 `stepDefense`를 돌린다. 각 단계 뒤에 가벼운 판정 `bigImpact(prev, next)`로 확인한다. 판정 대상은 필살기 명중, 충전 끊기, 영웅 근접의 무거운 적 처치, 보스 처치다. 걸리면 `stopAt`을 부르고 반복을 끊은 다음 바로 게시한다.

**불변식 확인**: 프레임 간격 8~43ms 무작위, 1·2배속, 판마다 멈춤 6번, 2,000번 실행.

| 검사 | 결과 |
| --- | --- |
| 멈춤 동안 돈 단계 | 0 |
| 멈춤이 끝난 첫 프레임의 단계 수 − 같은 간격 평소 단계 수 | 0 (몰아치기 없음) |
| 남은 단계를 버려서 생긴 실제 시간 지연 | 실행당 최대 0.15초(멈춤 6번 합) |
| 남은 단계를 되돌려 나중에 돌리는 변형 | 멈춘 뒤 최대 4단계 몰아치기 → 버리는 쪽을 택함 |

엔진은 같은 입력이면 같은 단계 순서로 돌기 때문에, 승패·보상·판 시간(엔진 시간)은 그대로다. 바뀌는 것은 실제 시간과의 대응뿐이다.

## 5. 발사점 보간의 조건 (46회차 제안 2)

46회차는 투사체를 처음 0.1초 동안 수정(무기 끝)에서 엔진 위치로 보간해 그리자고 했다. 영웅 투사체의 실제 비행 시간을 쟀다.
- 측정 범위: 4영웅 × 8스테이지 × 난이도 3 × 기본·전체 배치, 192판. 승리는 179판이다.
- 비행 시간은 발사부터 사라질 때까지다.

| 영웅 | 투사체 수 | 0.1초 미만 | 0.05초 미만 | 중앙값 | 하위 10% |
| --- | --- | --- | --- | --- | --- |
| 이안 | 2,862 | 8.7% | 6.0% | 0.23초 | 0.12초 |
| 리엘 | 6,557 | 8.7% | 3.2% | 0.25초 | 0.12초 |
| 청운 | 4,231 | 6.1% | 4.3% | 0.28초 | 0.13초 |
| 루나 | 2,989 | 6.4% | 4.1% | 0.27초 | 0.12초 |

- 6~9%는 보간이 끝나기 전에 맞는다. 그러면 그리는 위치가 맞는 순간 엔진 위치로 튄다.
- **보간 창 = min(0.1초, 비행 예정 시간 × 0.5)**로 한다. 비행 예정 시간은 투사체의 `duration`이다.
  - 그러면 늘 비행 중간까지 엔진 위치와 합쳐진다.
  - 명중 지점은 엔진과 같다.
  - 0.05초 미만인 짧은 비행은 수정에서 바로 적에게 가는 것처럼 보인다(1~2장).

## 7. 제안 (결정 불필요, 인계 A)

1. **히트스톱 구현 규격 (41·43 항목에 덧붙임)**
   - 4장의 `advanceClock`·`stopAt`을 쓴다.
   - 단계마다 `bigImpact`를 확인해, 사건 단계에서 반복을 끊고 남은 단계를 버린다.
   - 사건 상태는 게시 제한 없이 그 프레임에 게시한다.
   - 테스트
     - ① 멈춤 중 `steps` 0
     - ② 멈춤 뒤 첫 프레임의 단계 수가 같은 간격의 평소 단계 수 이하
     - ③ 사건 상태가 사건 프레임에 게시됨(`shouldPublishDefenseFrame`에 ‘강제’ 인자)
     - ④ 같은 대본 입력이면 멈춤 있음·없음의 최종 상태가 같음(408번 줄 방식)
   - 완료 판단: 60Hz·30Hz, 2배속에서 멈춘 그림이 사건 단계의 상태다(늦음 0).
2. **발사점 보간 창 (46회차 제안 2에 덧붙임)**: min(0.1초, `duration` × 0.5).
3. **64px 도구는 모든 칸을 본다**
   - 쌍마다 같은 번호 칸끼리 비교한다. 가장 나쁜 칸과 그 판정을 출력한다.
   - 걷기 두 칸(walk-a·walk-b) 중 하나라도 혼동이면 결과 코드 1이다. 맞는 모습·쓰러짐은 보고만 한다.
   - 지금 main에서는 돌·나무 walk-b(0.67)가 걸린다. 그래서 나무 병사 걷기 칸을 조금 더 다르게 해야 한다. 예: 몽둥이를 든 팔 각도를 걷기 두 칸에서 다르게 한다. 또는 B의 통나무안을 쓴다.
