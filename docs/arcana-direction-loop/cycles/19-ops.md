### 2-2. 입력이 없을 때의 루프 운영

사용자 결정과 개발 루프 산출물이 모두 없는 상태에서 3시간마다 긴 문서를 쓰면, 나중에 읽을 양만 늘어난다. 주기는 사용자가 정하는 것이므로 그대로 두고(18회차 질문), **회차의 분량**을 이 루프가 스스로 줄인다.

**저입력 회차 규칙(20회차부터)**: 지난 회차 이후 **사용자 결정도, 개발 브랜치 변경도 없으면**
- 네 분야 점검은 표 한 줄로 끝낸다.
- 주 분야에서는 **하나의 작은 단위**만 다룬다(설계서 하나 또는 정정 하나).
- 인계 목록과 README 기록은 그대로 갱신한다.
- 새 질문은 만들지 않는다.

둘 중 하나라도 생기면(결정이 오거나 개발 루프가 새 PR을 내면) 평소 회차로 돌아간다. 이 규칙은 README 회차 산출물 절에 적었다.

## 3. 모델링 설계

### 3-1. 상태 칩 알림 표시 규격

18회차 2-1의 ‘상태 칩에 엔진 알림 허용 목록 표시’를 개발 루프가 그대로 만들 수 있게 정한다. 그림이 아니라 화면 요소의 규격이다(16회차 바닥 표시와 같은 이유: 엔진 상태에서 바로 그린다).

| 항목 | 내용 |
| --- | --- |
| 자리 | 개발 브랜치 `DefenseBattle.tsx`의 `battle-input-note`(`role="status"`, 화면 아래 가운데, `max-width:95%`). 새 자리를 만들지 않는다. |
| 참고 | 개발 브랜치의 현재 동작: 돌진 조준 → “전장을 탭하면 돌진 · 전투는 계속돼요”, 몰려옴 → “무리가 몰려와요! 방어선을 단단히!”, 전술 정지 → “전술 선택 중 · 전투가 멈췄어요”. 이 셋은 지금처럼 **항상 우선**한다. |
| 허용 목록 | ① 보스 등장(4웨이브 시작, 보스가 있는 스테이지) ② 2·3웨이브 방어 성공 ③ 승리. 나머지 엔진 알림(건설 완료, 강화, 용병 합류 등)은 띄우지 않는다. 이미 다른 효과(건설·강화 연출)가 있기 때문이다. |
| 문구 | 한 번에 **22자 이하**(360px 한 줄). 넘으면 두 번에 나눠 차례로(18회차 2-2). 보스 등장은 대사 → 전술 안내 순. |
| 시간 | 알림 하나당 2.5초. 다음 알림은 앞의 것이 끝난 뒤. 대기열은 최대 2개, 넘치면 오래된 것을 버린다. 일시정지 중에는 시간이 흐르지 않는다. |
| 접근성 | `role="status"`(정중한 알림)를 유지한다. 같은 문구를 연속으로 다시 읽지 않는다. 동작 줄이기 설정에서는 나타남·사라짐 효과 없이 바로 바꾼다. |
| 색·모양 | 지금 상태 칩 모양 그대로. 보스 등장만 왼쪽에 보스의 예고색 점 하나(고목왕 주황, 서리군주 파랑, 파수꾼 주홍; 05·09회차). |
| 데이터 | 엔진은 지금처럼 `notice` 문자열을 쓴다. 화면은 엔진이 알림 종류를 함께 넘기도록(`noticeKind: 'boss' | 'wave-clear' | 'victory' | …`) 하나만 더 받아 허용 목록을 고른다. 문구를 화면에서 다시 만들지 않는다. |
| 완료 판단 | 360px 세로 화면에서 허용 목록 알림이 한 줄로 2.5초 보인다. 돌진 조준·몰려옴 중에는 알림이 그 뒤로 밀린다. 효과음 판단(`defenseSound.ts`)이 바뀌지 않는다. 기존 엔진 테스트가 통과한다. |
