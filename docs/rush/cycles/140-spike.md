## 문제

그래픽 설정이 ‘자동’이면 프레임이 느릴 때 전투 도중 높음 → 낮음으로 내려간다(`quality.ts`의 `AUTO`). 낮음은 해 그림자를 끄고, 표면 결 셰이더를 빼고, 마감 패스 없이 화면에 바로 그린다. 그래서 장면의 거의 모든 재질이 다른 셰이더 프로그램이 되어, 낮추는 그 프레임에 한꺼번에 컴파일된다. 128회차 탐침에서 소프트웨어 GL로 14개 남짓, 850 ms 프레임이었다. 낮춤은 이미 느린 기기에서 일어나므로 그 기기에서 가장 크게 끊긴다.

## 범위

- `RushView`: 전투 예열(128회차) 때, 설정이 ‘자동’이고 지금 높음이면 낮음 단계 프로그램도 컴파일한다. 낮음의 세 가지(해 그림자 끔, 표면 결 끔, 화면에 바로 그림)를 잠깐 켜고 `renderer.compile`을 부른 뒤 되돌린다. 그리는 것은 바꾸지 않는다(컴파일만, 다음 그림 전에 되돌림).
- `main.ts`: ‘자동’인지 알려 준다.
- 높음·낮음으로 고정한 사람은 바뀌지 않는다.

## 가설

자동 낮춤 순간의 링크가 0~몇 개로 준다. 대신 전투 시작 예열이 길어진다(낮음 단계 프로그램 수만큼).

## 수용 기준

- [x] 탐침(설정 ‘자동’, 소프트웨어 GL은 몇 초 안에 낮춤): 낮춤 틱 근처의 링크 수와 그 프레임 길이, 바꾸기 전·후
- [x] 시작 전 링크 수·시작 시간 증가를 숫자로
- [x] 높음 고정·낮음 고정은 시작 전 링크 수가 같다
- [x] `test:rush`, `tsc`, `build`, `smoke:rush` 통과

## 결과

`tools/rush-shader-probe.cjs`, 시연(시드 3, 속도 2) 45초, 설정 ‘자동’(기본값). 소프트웨어 GL은 5초쯤 높음 → 낮음으로 내려간다. 비교용으로 `?warmlow=0`이 낮음 예열을 끈다.

| | 낮음 예열 끔(`?warmlow=0`) | 낮음 예열 켬 |
| --- | --- | --- |
| 시작 전 링크 | 38 | 71~72 |
| 전투 중 링크 | 30 | 7 (모두 틱 62 안: 영웅 모델 예열과 그 낮음 변형) |
| 낮춤 순간(틱 509 근처) | **15개, 그 프레임 817 ms**, 이어 틱 617·643·669에 1~2개씩(400~667 ms 프레임) | **0개** |
| 낮춤 일어남 | 예 | 예(`autoDropped: true`, 끝 단계 낮음으로 따로 확인) |
| 가장 긴 프레임 | 817 ms | 667 ms (셰이더 링크 없음. 낮출 때 화면 버퍼·그림자 지도를 다시 만드는 일로 보임, 확인 안 함) |
| 페이지 열기 → 첫 틱 | 2.06초 | 2.28~2.31초 |

- 높음 고정(`?quality=high`)은 시작 전 링크 38, 낮음 고정은 33으로 전과 같다(‘자동’일 때만 낮음 예열).
- **넣은 것.** `RushView.prewarmLow`(main이 설정 ‘자동’일 때 켬)와 `warmLowTier()`. 전투 예열 프레임에서 지금이 높음이면, 해 그림자 끄기·표면 결 끄기·화면 대상(`setRenderTarget(null)`)으로 바꾼 채 `renderer.compile`을 부르고 곧바로 되돌린다. 그리는 일은 없다. 영웅 모델이 늦게 받아질 때도 같은 방법으로 두 단계 모두 예열한다.
- 대가: 시작 때 프로그램 33~34개를 더 컴파일한다(소프트웨어 GL에서 시작이 약 0.25초 늦음, 한 번씩 잼). 프로그램이 79~80개로 늘어 GPU 메모리를 조금 더 쓴다. 낮춤이 일어나지 않는 빠른 기기도 ‘자동’이면 이 값을 치른다.
- 휴대폰에서 낮춤 순간이 얼마나 덜 끊기는지는 모른다(실기기 측정, 백로그 1과 함께).

## 검증

- `npm run test:rush`: 147개 통과(설계 기둥 포함). `npx tsc --noEmit`, `npm run build`: 통과. `npm run smoke:rush`: 41개 통과, 실패 0(‘자동 품질 낮춤’ 검사 포함). 높음 전투 스크린샷 직접 확인(그림자·마감 그대로).
