## 문제

전투 화면은 3D 캔버스 위에 DOM HUD를 얹는다. 매 프레임 `main.ts`는 아래 순서로 DOM을 읽고 쓴다.

1. 시뮬레이션 이벤트로 피해 숫자·알림을 만든다(쓰기).
2. `updatePops`는 캔버스 위치를 읽고(`getBoundingClientRect`), 숫자마다 위치·투명도를 쓴다.
3. `updateCallout`은 캔버스 위치를 다시 읽는다(35회차).
4. `updateHud`는 체력 막대, 탄 칸, 필살기 고리, 버튼 상태를 쓴다. 같은 값이어도 매 프레임 쓰는 것이 있다.
5. `seeThroughHud`는 HUD 상자 5개와 캔버스 위치를 읽고(23회차), 반투명 표시를 쓴다.

쓰기 뒤에 읽기가 오면 브라우저는 그 자리에서 스타일·레이아웃을 다시 계산해야 한다(강제 동기 레이아웃). 위 순서에서는 이런 일이 한 프레임에 여러 번 생길 수 있다. 휴대폰에서는 이것이 프레임 시간을 잡아먹는다.

## 범위

- **읽기를 프레임 맨 앞으로 모은다.** 캔버스 위치와 HUD 상자는 프레임 처음, 아무것도 쓰기 전에 한 번만 읽는다. 그 프레임의 함수들은 이 값을 같이 쓴다. HUD 상자는 한 프레임 전 모습이지만 반투명 판정에는 충분하다.
- **같은 값은 다시 쓰지 않는다.** 체력 막대 `transform`, 탄 칸 `--fill`, 필살기 `--charge`처럼 매 프레임 쓰던 인라인 스타일은 값이 바뀔 때만 쓴다(`setText`처럼).
- 화면과 동작은 바뀌지 않아야 한다. 규칙은 바꾸지 않는다.

## 측정

Chrome 성능 지표(`Performance.getMetrics`)의 `LayoutCount`, `RecalcStyleCount`를 자동 시연 전투(휴대폰 가로, 시드 3, 높음 품질) 5초 동안 재서 애니메이션 프레임 수로 나눈다. `getBoundingClientRect` 호출 수도 센다. 시간(ms)은 소프트웨어 렌더링 컨테이너라 주장하지 않고 횟수만 비교한다.

## 가설

지금은 프레임마다 레이아웃이 2번 이상(그리기 1번 + 강제 1번 이상) 일어난다. 읽기를 앞으로 모으면 프레임당 약 1번이 된다. 스타일 다시 계산도 준다.

## 수용 기준

- [x] 전투 중 프레임당 `LayoutCount`가 준다(목표 약 1). `getBoundingClientRect` 호출이 프레임당 몇 번으로 준다 → 레이아웃은 전부터 프레임당 0.2라 그대로다. 읽기는 6 → 0.4~1.0, 스타일 계산은 시연에서 1.2 → 0.4로 줄었다(아래)
- [x] 반투명 HUD, 피해 숫자, 보스 말풍선이 전과 같이 동작한다(스모크, 스크린샷)
- [x] `test:rush`, `tsc`, `build`, `smoke:rush` 통과

## 바꾼 것 (`main.ts`만)

- **읽기 묶기**
  - `readLayout()`을 프레임 맨 처음, 아무것도 쓰기 전에 부른다. 캔버스 위치(`canvasRect`)와 HUD 상자 5개(`hudBoxes`)를 읽는다.
  - 12프레임마다 한 번 읽는다. 창 크기가 바뀌거나(`resize`) 전투에 막 들어와 HUD 상자가 비었거나 크기가 0이면 바로 읽는다.
  - `updatePops`, `updateCallout`, `bossCallout`, 반투명 HUD 판정(`seeThroughHud` → `enemyScreen`), 마을 표지 배치(`town.layout`)는 이 값을 쓴다. 입력(터치·마우스 좌표)은 지금처럼 그때그때 읽는다.
- **바뀔 때만 쓰기**
  - `setStyle`과 `setFlag`를 더했다(`setText`와 같은 방식). 체력 막대 `transform`, 탄 칸 `--fill`, 필살기 `--charge`, 버튼의 `hidden`·`disabled`를 값이 바뀔 때만 쓴다.
  - 탄 칸·필살기 값은 소수 셋째 자리까지만 쓴다.
- 규칙·화면 변경 없음.

## 결과 (휴대폰 가로, 5초, 두 번 잰 값)

| | 전 | 후 |
| --- | --- | --- |
| 시연 전투: 레이아웃 / 프레임 | 0.21~0.31 | 0.19~0.21 |
| 시연 전투: 스타일 계산 / 프레임 | 1.16~1.23 | **0.38~0.40** |
| 시연 전투: `getBoundingClientRect` / 프레임 | 6.00 | **0.43~0.44** |
| 직접 조작(마우스 연사): 레이아웃 / 프레임 | 0.16~0.20 | 0.19 |
| 직접 조작: 스타일 계산 / 프레임 | 1.00 | 0.93 |
| 직접 조작: `getBoundingClientRect` / 프레임 | 6.59~6.64 | **0.96~1.06** |

- **가설은 일부 틀렸다.** 레이아웃은 전부터 프레임당 0.2번이었다. 위치·투명도만 바꾸는 쓰기(`transform`, `opacity`)는 레이아웃을 부르지 않기 때문이다. 강제 레이아웃이 여러 번 생긴다는 예상은 맞지 않았다.
- 실제로 준 것은 스타일 다시 계산과 레이아웃 읽기 호출이다.
  - 시연에서 스타일 계산이 프레임당 1.2번에서 0.4번으로 줄었다. 같은 값을 매 프레임 다시 쓰던 인라인 스타일 때문이었다.
  - 직접 조작에서는 0.93번이다. 쏘면 탄 칸이 매 프레임 차오르므로 실제로 값이 바뀌어서다.
- 직접 조작에 남은 `getBoundingClientRect` 약 0.5번은 마우스 클릭마다 입력이 화면 좌표를 땅 좌표로 바꾸며 읽는 것이다.
- 시간(ms)은 소프트웨어 렌더링 컨테이너라 주장하지 않는다. 실기기 게이트에서 잰다.

## 동작 확인

- **반투명 HUD**: 23회차 측정을 그대로 다시 돌렸다(시연 60초, 250ms마다).
  - 화면 안 적 651마리 중 58마리(8.9%)가 HUD 아래를 지났다. 불투명한 HUD에 가려진 적은 0이다.
  - `?nofade`(반투명 끔)에서는 67/657(10.2%)이 모두 가려졌다. 23회차 결과(0%)와 같다.
  - 읽기가 최대 12프레임 늦어도 판정에 문제가 없었다.
- **보스 말풍선**: 35회차 장면을 다시 찍었다. 말풍선 자리(휴대폰 378, 168 / 데스크톱 596, 341)가 35회차와 같고, 가린 보스 화소는 0이다.
- 피해 숫자와 반투명 HUD가 함께 보이는 전투 화면을 직접 열어 확인했다.
