## 질문

킹샷식 PvE는 나중에 적 수가 지금(웨이브 최대 약 21마리)보다 크게 늘 수 있다. 그때 시뮬레이션을 ECS(구조체 배열 레이아웃, bitECS·Koota)로 옮겨야 하는가, 아니면 지금 구조(객체 배열 + 결정적 `sim.ts`)로 충분한가?

## 범위 (시간 제한 스파이크, 제품 코드는 바꾸지 않음)

1. **확장성 측정 도구** `tools/rush-bench.ts`: 실제 `stepRush`에 적 N마리(25, 100, 300, 1000)를 넣고 스텝당 시간과 GC 횟수를 잰다. 탑 4개 Lv3, 영웅 대기, 마을이 무너지지 않게 둔다.
2. **핫스팟**: N=300에서 CPU 프로파일을 떠서 함수별 자체 시간 비중을 본다.
3. **레이아웃 대 알고리즘**: 가장 무거운 루프를 스크래치에서 세 가지로 비교한다.
   - 지금처럼 객체 배열
   - ECS식 타입 배열(SoA)
   - 객체 배열 + 공간 격자
4. **비용**: bitECS를 스크래치에 받아 최소 사용 번들 크기(gzip)를 잰다. 저장소 의존성에는 넣지 않는다.

## 가설

지금 규모에서는 ECS가 필요 없다. 적이 많아질 때 먼저 터지는 것은 레이아웃이 아니라 적끼리 밀어내기의 O(N²) 쌍 검사이고, 이것은 ECS가 아니라 공간 격자로 고친다.

## 수용 기준

- [x] N별 스텝당 시간(중앙값)·GC 횟수 표. 절대 시간은 컨테이너 CPU 기준 참고값이고, 기기 성능 주장은 하지 않는다. 증가 모양(선형인가 제곱인가)을 본다
- [x] N=300 핫스팟 상위 함수와 비중
- [x] 같은 루프의 객체·SoA·격자 비교
- [x] 결론: 채택·보류·기각과 재검토 조건을 [조사 문서](../engine-research-2026-11.md)에 반영
- [x] 제품 코드 변경 없음. `test:rush`, `tsc`, `build`, `smoke:rush` 통과(도구 파일 추가만)

## 결과

모든 시간은 이 컨테이너 CPU에서 Node로 잰 중앙값(5묶음)이다. 휴대폰 성능을 주장하지 않는다. 볼 것은 **증가 모양**과 **변형 사이의 비율**이다.

### 1. 확장성 (`node --experimental-strip-types tools/rush-bench.ts`)

적 N마리(죽지 않음), 탑 4개 Lv3, 영웅 대기. 지금 웨이브의 최대는 약 21마리다.

| 적 N | ms/스텝 | GC/1000스텝 | 밀어내기 쌍 검사/스텝 |
| ---: | ---: | ---: | ---: |
| 25 | 0.075 | 89 | 300 |
| 100 | 0.248 | 201 | 4,950 |
| 300 | 1.733 | 500 | 44,850 |
| 1000 | 16.233 | 2,537 | 499,500 |

- N을 3.3배(300 → 1000) 늘리면 시간은 9.4배가 된다. **제곱에 가깝다.**
- 1000마리에서는 한 스텝이 60fps 한 프레임(16.7ms)을 혼자 다 쓴다(컨테이너 기준).
- GC 횟수는 실행마다 흔들린다(N=300에서 500, 프로파일러를 켠 실행에서는 826). 경향만 본다.

### 2. 핫스팟 (N=300, `--cpu-prof` 자체 시간)

| 비중 | 함수 |
| ---: | --- |
| 60.9% | `len` = `Math.hypot` (sim.ts:95) |
| 18.8% | `updateEnemies` (적끼리 밀어내기 이중 루프 포함) |
| 8.0% | `stepRush` (인라인된 나머지) |
| 5.6% | GC |
| 1.7% | `confine` |

`updateEnemies`의 밀어내기는 **모든 쌍에 `Math.hypot`을 먼저 계산한 뒤** 겹치는지 본다. 겹치지 않는 쌍이 대부분인데도 비싼 제곱근을 매번 부른다.

### 3. 레이아웃 대 알고리즘

**(a) 실제 `stepRush`의 변형** (스크래치 복사본, 같은 도구)

| 적 N | 지금 | A: 거리 제곱으로 먼저 거르기 | B: A + 2.4m 격자 |
| ---: | ---: | ---: | ---: |
| 25 | 0.075 | 0.076 | 0.072 |
| 100 | 0.248 | 0.140 | 0.139 |
| 300 | 1.733 | 0.721 | 0.529 |
| 1000 | 16.233 | 6.104 | 1.929 |

- **A는 결과가 비트 단위로 같다.** 시드 1~5 전체 판을 `guardBot`으로 돌린 `rushHash`가 다섯 개 모두 지금과 같고, `sim.test.ts`도 통과한다. 겹치는 쌍에서는 원래 식을 그대로 쓰기 때문이다.
- **B는 쌍을 보는 순서가 바뀌어 결과가 아주 조금 달라진다.** 시드 2는 8587 → 8588틱에 끝났다. 넣으려면 밸런스 테스트를 다시 확인해야 한다.

**(b) 같은 밀어내기 루프만 떼어 객체 배열(지금)과 타입 배열(ECS식 SoA) 비교** (스크래치 `layout/bench.mjs`, 둘 다 A 적용)

| 적 N | 객체 배열 | 타입 배열 |
| ---: | ---: | ---: |
| 100 | 0.021 | 0.027 |
| 300 | 0.168 | 0.240 |
| 1000 | 1.963 | 1.692 |

- 레이아웃만 바꾸면 300마리까지는 오히려 느리고, 1000마리에서 14% 빠르다. 알고리즘을 고친 이득(A 2.7배, B 8.4배)에 비하면 작다.

### 4. ECS 라이브러리 비용 (스크래치 설치, 저장소 의존성 아님)

| 라이브러리 | 버전 | 최소 사용 번들 (min / gzip) |
| --- | --- | --- |
| bitECS | 0.4.0 | 12.2 KB / 4.6 KB |
| Koota | 0.6.6 | 36.4 KB / 11.0 KB |

번들 크기는 문제가 아니다. 비용은 옮기는 일이다.
- `sim.ts`의 모든 규칙과 테스트를 다시 써야 한다.
- 결정성을 다시 지켜야 한다. 엔티티 id 재사용과 쿼리 순서가 `rushHash`와 판 결과를 바꾼다.
- 서버 재사용(같은 `sim.ts`로 판정)을 위한 순수 TS 구조를 다시 맞춰야 한다.

## 판정

- **ECS: 보류.** 지금 규모(수십 마리)와 다음 규모(수백 마리)에서 병목은 데이터 레이아웃이 아니라 O(N²) 쌍 검사와 `Math.hypot`이다. ECS로 옮겨도 이 둘은 그대로 남는다.
- **먼저 할 것(성능·모바일 레인 백로그로 넘김)**
  1. 밀어내기에 거리 제곱 거르기를 넣는다(A). 결과가 같아 밸런스 영향이 없다.
  2. 적이 300마리를 넘는 웨이브를 계획할 때 격자(B)를 넣고, 밸런스 테스트를 다시 확인한다.
- **ECS를 다시 볼 조건**
  - 알고리즘을 고친 뒤에도 프로파일이 레이아웃(캐시 미스) 쪽을 가리킬 때
  - 상태이상·투사체처럼 조합이 많은 엔티티가 수천 개가 될 때
  - 시뮬레이션을 워커·WASM으로 옮길 때
