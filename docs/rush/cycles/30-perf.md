## 범위 (바꾼 후보)

표에서 보듯, 오히려 **타이틀 화면이 전투 장면 전체(44 드로콜, 3.2만 삼각형)를 매 프레임 다시 그린다**. 타이틀 카드 뒤 배경은 흐리게 멈춘 전장이다. 결과 화면과 일시정지 화면도 같다. 휴대폰에서는 메뉴에 머무는 동안 배터리와 발열만 쓴다.

- **메뉴 화면(타이틀·결과·일시정지)에서는 4 프레임에 한 번만 3D 장면을 그린다.** 메뉴에 들어간 첫 프레임은 바로 그린다.
- 창 크기가 바뀌거나 그래픽 품질을 바꾸면(캔버스가 지워진다) 다음 프레임에 바로 그린다.
- 전투(플레이·시연)와 마을 화면은 지금처럼 매 프레임 그린다.
- 규칙은 바꾸지 않는다.

## 측정

화면마다 3초 동안 브라우저 애니메이션 프레임 수와 실제로 그린 프레임 수(`renderer.info.render.frame`)를 센다. 비율로 비교한다. 컨테이너는 소프트웨어 렌더링이라 FPS나 전력은 주장하지 않는다.

## 수용 기준

- [x] 타이틀·일시정지·결과에서 그린 프레임 / 애니메이션 프레임이 약 1 → 약 0.25로 준다. 전투는 1 그대로
- [x] 메뉴 화면이 전과 같아 보인다(스크린샷). 일시정지에서 그래픽 품질을 바꿔도 화면이 비지 않는다
- [x] `test:rush`, `tsc`, `build`, `smoke:rush` 통과

## 바꾼 것

- **`main.ts`**
  - 메뉴 상태(타이틀, 결과, 플레이 중 일시정지)이면 `menuFrames`를 세어 4 프레임에 한 번만 `view.render()`를 부른다. 장면 갱신(`view.sync`)과 HUD 갱신은 지금처럼 매 프레임 한다.
  - `resize()`와 그래픽 품질 변경(`applyQuality`)은 `forceDraw`를 켠다. 다음 프레임에 바로 그린다.
  - 디버그 손잡이 `__rush.drawnFrames`(그린 프레임 수)를 더했다.
- 규칙·테스트 변경 없음.

## 결과 (휴대폰 가로, 화면마다 3초)

WebGL 그리기 함수를 감싸, 무엇이든 그린 애니메이션 프레임의 비율을 셌다. 전후 같은 방법이다.

| 화면 | 전: 그린 프레임 / 애니메이션 프레임 | 후 |
| --- | --- | --- |
| 타이틀 | 59 / 59 (1.00) | **46 / 181 (0.25)** |
| 마을 | 51 / 51 (1.00) | 78 / 78 (1.00) |
| 전투 | 41 / 41 (1.00) | 37 / 37 (1.00) |
| 일시정지 | 39 / 39 (1.00) | **36 / 146 (0.25)** |
| 결과 | 38 / 38 (1.00) | **39 / 155 (0.25)** |

- 메뉴 세 화면에서 3D 그리기가 4분의 1로 준다. 전투와 마을은 그대로다.
- 컨테이너(소프트웨어 렌더링)에서는 그리기가 줄자 메뉴의 애니메이션 프레임 수가 3초에 59 → 181로 늘었다. 기기의 배터리·발열·FPS는 주장하지 않는다. 실기기 게이트에서 잰다.
- 일시정지에서 그래픽 품질을 바꿔 캔버스가 지워져도, 다음 프레임에 바로 다시 그려 배경이 비지 않았다(스크린샷 확인).
- 결과 화면은 전과 거의 같다. 다른 화소 265개는 효과 시점 차이다.
