## 문제

러시는 three.js `0.186.1`을 쓴다(캠페인과 같은 의존성). npm 최신은 `0.187.0`(2026-10-30 배포)이다. 올릴지 판단할 자료가 없다. 러시는 툰 재질, 잉크 외곽선(뒤집은 껍데기), 인스턴스 배치, GLB 부품 굽기, 품질 단계(픽셀 비율)를 쓰므로 렌더러 변경에 민감하다.

## 범위

- **측정만 한다.** 저장소 사본을 스크래치에 만들고, 거기서만 `three@0.187.0`(과 맞는 `@types/three`)을 설치한다. 저장소의 `package.json`·잠금 파일은 바꾸지 않는다(공유 파일, 올리려면 사용자 확인).
- 잴 것
  1. `tsc`: 타입 오류 수
  2. `test:rush`, `smoke:rush` 통과 여부
  3. 빌드 크기: three 덩어리(원본·gzip) 전후
  4. 같은 장면 화면 차이: 고정 시드·틱으로 멈춘 전투 장면(데스크톱·휴대폰), 마을, 모델 시트를 두 버전으로 찍어 다른 화소 수를 센다
  5. 바뀐 점: r187 릴리스 노트에서 러시가 쓰는 API에 닿는 항목
- 결과는 이 기록에 남기고, 올릴지는 사용자 결정으로 넘긴다(캠페인도 같은 three를 씀).

## 추천 (사용자 결정용)

**보류.** 러시에는 위험이 낮지만 이득도 없다.

- 화면·타입·테스트가 같고 크기는 +0.3%다. 러시가 쓸 새 기능도 없다.
- three는 캠페인과 함께 쓰는 의존성이다. 올리려면 공유 파일(`package.json`, 잠금 파일)을 바꾸고 캠페인 모델 작업실(PMREM)도 확인해야 한다.
- 캠페인 쪽 작업 때 함께 올리기를 추천한다. 러시 쪽 확인 절차는 이 기록의 사본 방법을 다시 쓰면 된다(약 10분).

## 사고 기록

사본을 만들 때 `rsync`가 컨테이너에 없어 명령 묶음이 중간에 멈췄다. 그 바람에 뒤의 `npm install --no-save three@0.187.0 @types/three@0.187.0`이 **사본이 아니라 저장소 폴더에서** 돌았다.

- 저장소 `node_modules`의 `@types/three`가 잠깐 0.187.0이 됐다(three는 0.186.1 그대로).
- `package.json`과 잠금 파일은 바뀌지 않았다(`git status` 확인).
- 바로 `npm ci`로 잠금 파일대로 되돌렸다(three 0.186.1, `@types/three` 0.186.0 확인). 그 뒤 저장소에서 `test:rush`·`tsc`·`build`·`smoke:rush`를 다시 돌려 모두 통과했다.
- 다음부터 스크래치 사본은 `tar`로 만들고, 설치 명령은 사본 폴더 확인(`pwd`) 뒤에만 잇는다.
