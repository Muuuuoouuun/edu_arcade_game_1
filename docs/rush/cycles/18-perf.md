## 범위

13회차 프로파일에서 적 300마리일 때 자체 시간의 61%가 `Math.hypot`이었다. 대부분은 적끼리 밀어내기 이중 루프에서 모든 쌍의 거리를 먼저 계산한 탓이다.

- 밀어내기에서 **거리 제곱으로 먼저 거른다**. 겹치는 쌍에서만 원래 식(`len`)으로 거리를 구해 밀어내기 값은 그대로다.
- 시간이 남으면 같은 방식을 탑의 사거리 검사에 적용한다. 단, 결과가 같을 때만 넣는다.
- 격자(13회차 변형 B)는 결과가 달라지므로 이번에 넣지 않는다.

## 가설

판 결과가 비트 단위로 같고, 적 300마리 이상에서 스텝 시간이 2배 넘게 준다.

## 수용 기준

- [x] **결과 동일**: 스테이지 1·5·10 × 두 영웅 × 시드 1~5(30판)를 끝까지 돌린다. 1초마다 찍은 `rushHash`의 묶음 해시가 전후 모두 같다
- [x] `tools/rush-bench.ts` 전후 표(컨테이너 CPU 참고값, 기기 성능 주장 아님)
- [x] `test:rush`(설계 기둥 포함), `tsc`, `build`, `smoke:rush` 통과

## 바꾼 것

`sim.ts` `updateEnemies`의 밀어내기 이중 루프에 거리 제곱 검사를 먼저 넣었다(3줄). 겹치는 쌍에서는 원래대로 `len`으로 거리를 구하므로, 밀어내는 양과 순서가 같다. 다른 코드는 바꾸지 않았다.

## 결과

**결과 동일 (30판)**
- 대상: 스테이지 1·5·10 × 궁수·브론 × 시드 1~5를 `guardBot`으로 끝까지 돌렸다.
- 방법: 1초(60틱)마다 `rushHash`를 이어 붙여 SHA-1을 만들고, 전후를 `diff`로 비교했다.
- 결과: **30판 모두 같다.** 판 결과는 이긴 판 20, 진 판 10이다(스테이지 10은 모두 짐). 이것도 전후가 같다.

**스텝 시간** (`tools/rush-bench.ts`, 중앙값 ms, 컨테이너 CPU 참고값이며 기기 성능 주장은 아니다. 전후를 번갈아 두 번씩 돌렸다)

| 적 N | 전 (1회 / 2회) | 후 (1회 / 2회) | 배율 |
| ---: | ---: | ---: | ---: |
| 100 | 0.267 / 0.259 | 0.164 / 0.144 | 약 1.7× |
| 300 | 1.798 / 1.822 | 0.708 / 0.794 | 약 2.4× |
| 1000 | 17.614 / 17.178 | 7.388 / 6.735 | 약 2.5× |

- 따로 한 번 더 돌린 ‘후’ 측정에서 300마리가 1.191로 튀었다. 컨테이너 잡음으로 보고 표에서는 번갈아 돌린 두 번만 쓴다.
- GC 횟수(1000스텝당)는 300마리에서 약 500 → 140으로 줄었다. `Math.hypot` 호출이 줄면서 할당이 줄어든 것으로 보인다(원인은 확인하지 않았다).
- 지금 웨이브 규모(최대 약 21마리)에서는 차이가 잡음 안이다(25마리 전 0.081, 후 0.074·0.097ms). 이번 변경은 적이 많은 웨이브를 위한 대비다.

**다음 병목 (N=300 프로파일, 변경 뒤)**

| 비중 | 위치 |
| ---: | --- |
| 47.5% | `updateEnemies`. 대부분 밀어내기 이중 루프의 반복 자체(sim.ts:528, 530) |
| 18.0% | `len`. 겹치는 쌍의 실제 거리 |
| 15.2% | `stepRush`(인라인된 나머지) |
| 4.6% | `confine` |

남은 비용은 O(N²) 반복 자체다. 격자(13회차 변형 B)로만 줄일 수 있고, 쌍을 보는 순서가 바뀌어 결과가 달라진다. 300마리가 넘는 웨이브를 만들 때 밸런스 테스트와 함께 넣는다. 탑 사거리 검사는 `dist` 2% 정도라 손대지 않았다.
