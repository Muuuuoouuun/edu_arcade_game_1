# 모바일 게임 앱 전환과 최신 소스 기준

확인일: 2026-11-06 (KST). 아래 브랜치·도구·용량은 이번 통합 시점의 스냅샷이며 매 작업 시작 시 다시 확인한다. 현재 게임은 React 19 + Vite + TypeScript 웹 앱이다. 전투는 SVG/HTML과 Blender에서 구운 2.5D 스프라이트를 사용하고, Three.js는 별도 모델 작업실에서 사용한다. 이 문서는 APK나 iOS 앱 제작 완료를 의미하지 않는다.

다른 저장소로 이동하지 않았다. 허브와 아르카나 디펜스는 [Muuuuoouuun/edu_arcade_game_1](https://github.com/Muuuuoouuun/edu_arcade_game_1)에 있다.

개발 브랜치는 당시 main보다 76커밋 앞섰고, 기획 브랜치는 같은 기준에서 40커밋을 별도로 쌓았다. PR #28~#59의 대상은 개발 통합 브랜치였다. 이번 통합은 양쪽 이력을 보존해 main에 함께 반영하기 위한 것이다. 기획의 모델 초안은 `docs/arcana-direction-loop/model-drafts/`에 남으며 게임 런타임 에셋으로 자동 채택하지 않는다. 회차 문서의 제안·측정·구현 상태를 구분하고, 실제 구현 여부는 최신 코드를 우선한다.

환경의 fetch 설정은 `main`만 가져오고 있었다. `git ls-remote --heads origin`으로 실제 전체 브랜치를 확인하고 전체 브랜치를 fetch했다. 이후 작업은 PR의 base를 **명시적으로 main**으로 지정한다. 기획 브랜치의 이후 변경은 다시 비교·검토한 뒤 통합한다. 별도 서비스의 기획 예약 작업을 이 변경이 수정하거나 재등록하지는 않는다.

다른 두 저장소는 계속 별도다. `math_speed/app`에는 Flutter 도메인·앱 골격이 있고 웹 허브는 `math_speed/functions/src/mathEngine.ts`를 공유한다. 그 Flutter 코드에 아르카나 디펜스가 옮겨진 것은 아니다. `Word_check`는 단어 숙제 관리용 Node/SQLite 프로젝트다.

## 선택한 경로: 기존 게임으로 Android 설치판부터

2026-11-06 사용자가 Android 설치판 우선 경로를 선택했다. 같은 저장소에 Capacitor Android 셸·네이티브 뒤로가기/백그라운드 정지·진동 연결을 추가했다. 현재 제작·검증 범위와 명령은 [Android 시험 설치판](android-install.md)을 따른다. 아래 표는 전체 전환의 완료 기준이며 첫 APK가 모든 단계의 완료를 의미하지 않는다. Godot 전환은 이번에 진행하지 않는다.

현재 2.5D 전투와 자산을 재사용하는 **Capacitor 기반 Android 시험판**을 첫 선택으로 추천한다. 새로운 GitHub 저장소를 만들 필요 없이 같은 저장소에 Android 프로젝트를 추가할 수 있다. 이 경로는 설치·실행 기반을 제공하며, 그래픽과 게임성의 완성도는 아래 별도 제작 기준을 통해 높인다.

| 단계 | 제작 범위 | 완료 판단 |
| --- | --- | --- |
| 1. 설치 가능한 앱 | Capacitor 설정, Android 셸, 앱 ID·아이콘·스플래시, 로컬 웹 번들 | 디버그 APK를 실제 Android에 설치해 서버 없이 시작. 원격 개발 URL을 제품 앱에 넣지 않음 |
| 2. 앱 생활주기 | Android 뒤로가기, 안전 영역, 회전, 잠금·통화·백그라운드 복귀, 소리·진동 | 전투가 배경에서 진행되지 않고 복귀 시 명시적으로 재개. 뒤로가기로 진행 상황을 잃지 않음 |
| 3. 저장·오프라인 | 캠페인/설정 저장과 버전 이행, 강제 종료·업데이트 후 복원, 전투 중 저장 정책 | 네트워크 없이 첫 원정·보상·재실행 가능. 기존 브라우저 저장이 설치 앱으로 자동 이전된다고 가정하지 않음 |
| 4. 게임 화면·아트 | 이미지 중심 거점, 별도 전투, 손가락 조작, 인물·몬스터 실루엣과 공격 준비/타격/회복 | 360px 기준 역할·위협·공격 시점을 읽고 조작 가능. 실제 플레이 크기의 전후 화면으로 판단 |
| 5. 성능·출시 | 자산 분할, 기기별 품질, 프레임·메모리·발열 측정, 서명·스토어 준비 | 대표 중급 Android에서 실측. 목표 60fps, 필요 시 30fps 모드. 개발 APK와 서명된 출시 AAB를 구분 |

현재 전체 웹 `dist`는 약 57MiB이며 방어 게임 자산만 약 35MiB다(`npm run build` 후 각각 `du -sh dist`, `du -sh dist/defense`로 측정한 디스크 사용량, 압축 설치 크기 아님). 모델 작업실용 GLB·원본 렌더와 다른 실험 화면을 제품 앱에 얼마나 포함할지 정하고, 초기 플레이에 필요한 자산을 분리한다. WebP 크기 감소만으로 프레임 성능 향상을 단정하지 않는다. iOS 검증은 macOS/Xcode·서명·실기기 경로가 필요하다.

## 게임 엔진을 선택할 경우

Godot 기반 제작은 전투 렌더링·애니메이션·입력·효과 관리와 네이티브 내보내기를 한 엔진에서 다루는 대안이다. 현재 React UI와 TypeScript 전투 엔진은 자동 변환되지 않는다. Blender 원본·스프라이트·스테이지 데이터·회귀 시나리오는 재사용하고, 전투와 UI는 단계적으로 이식해야 한다.

이 경로를 선택하면 먼저 **영웅 1명 + 적 3종 + 타워 3종 + 스테이지 1개**를 실제 기기에서 검증한다. 탭 이동·돌진·타격감·프레임·불러오기 시간을 기존 버전과 비교한 후 확대한다. 전체 게임을 먼저 재작성하거나 엔진 도입만으로 상용 게임 수준을 달성했다고 판단하지 않는다. 현재 환경에서 `/opt/godot/4.6.3/Godot_v4.6.3-stable_linux.x86_64 --version` 출력 `4.6.3.stable.official.7d41c59c4`를 확인했으나 이 저장소에 게임 프로젝트나 Android 내보내기를 구현한 상태는 아니다.

## 제품 품질 기준

준비 화면은 컨셉 아트와 성장·다음 목표 중심, 스테이지는 전투 중심이다. 재미를 먼저 검증하고 재료 상성·관찰노트는 최소·선택형 교육으로 유지한다. 참고작에서는 거점 성장, 빠른 터치 반응, 역할 실루엣, 공격 예고·피격·회복 리듬을 기준으로 삼는다. 플랫폼 선택과 별개로 이 부분을 계속 개선한다.

이번 통합의 검사 결과와 PR은 해당 변경 설명 및 작업 증거에 기록한다. 브라우저 화면 검증을 APK 설치나 실기기 성능 검증으로 표시하지 않는다.
