## 회차 절차

1. **원격 최신 작업 파악**
   - `git fetch origin main` 과 작업 브랜치 fetch. 게임 상태의 기준은 **origin/main**이다.
   - GitHub PR 목록(최근 병합 10여 개 + 열린 PR)을 확인하고, 지난 회차 기준 SHA 이후 병합된 PR을 표로 적는다. 열린 PR이 규칙·수치를 바꾸면 “예정 변경”으로 따로 적는다.
   - 작업 브랜치의 PR이 이미 병합됐다면 최신 main에서 같은 이름으로 브랜치를 다시 시작한다.
2. **세 분야 짧은 점검** — 분야별 현재 상태 1줄 + 발견 1~3개(근거 파일 경로·줄).
3. **주 분야 깊은 설계** — 측정(숫자) → 진단 → **제안**(작업 가정) → 세 축 판단 → 수용 기준. 사용자 결정이 필요한 것은 **결정 대기**로.
4. **인계 후보** — 개발 쪽이 바로 고를 수 있는 작은 단위. 각 항목에 우선순위(P0/P1/P2), 결정 필요 여부, 완료 판단(테스트로 확인할 것)을 적는다.
5. **사용자에게 물을 것** — 최대 3개. 이미 대기 중인 질문은 반복하지 않는다.
6. 이 README의 **회차 기록·결정 대기·다음 회차 후보** 갱신.
7. 커밋 `docs(rules-loop): cycle NN — <분야> <요약>` 후 `git push -u origin claude/pensive-ptolemy-uhyunb`.

### 저입력 회차

지난 회차 이후 **새 병합 PR도, 사용자 결정도 없으면** 짧게 쓴다: 세 분야 점검은 표 한 줄씩, 주 분야는 측정 하나 또는 설계서 하나, 새 질문 없음. 둘 중 하나라도 생기면 평소 회차로 돌아간다.

**v1에서 이어받는 제약** (사용자 승인 없이 넘지 않는다):

- 학습·관찰은 승리·보상·진행의 관문이 아니다. 속성 대응은 효율·표시·발견으로 보상한다.
- 영웅·용병·펫은 피해·죽음 없음. 타워 체력·파괴·수리는 v1에 없다.
- 새 재화·확률 강화·유료 수리·입장 에너지를 넣지 않는다. 강제 제한 시간·대기 타이머 없음.
- 모바일은 가로 화면만(가로 배율 0.505~0.572).
- 규칙은 반드시 **전투 전 예고**(예보·지형 표시)와 **화면 표시**가 함께 있어야 한다. 보이지 않는 규칙은 넣지 않는다.

`cycles/NN-<분야>.md`:

1. 기준 — 회차, KST 시각, 기준 커밋(origin/main SHA), 주 분야, 지난 회차 이후 병합 PR.
2. 세 분야 짧은 점검.
3. 주 분야 측정과 진단 — 숫자는 `measurements/NN/` 의 스크립트·결과로 재현 가능해야 한다.
4. 설계 제안 — **제안**/**결정** 표시, 세 축 판단, 수용 기준.
5. 인계 후보.
6. 사용자에게 물을 것.
