# 물폭탄포의 상부 조준과 포신 반동

2026-11-06 컨셉 기반 반복 개발의 세 번째 회차에서 Lv.2를 구현하고, 네 번째 회차에서 Lv.3 최종 강화까지 연결했다. `main`의 `03b6a70` 보스 충격파·문구 수정을 개발 브랜치에 보존하고, Claude 브랜치 `a8d95fe`의 발사 직전 재조준 기획과 현재 타워 엔진을 기준으로 연결했다.

전달 전 원격 재확인에서 `main`의 `40d2289`(약점 명중 집계)와 Claude `78b4afd`의 41회차 애니메이션·타격 기획을 확인했다. main 변경은 개발 브랜치에 통합했다. 상태 타입의 충돌은 기존 보행·돌진 필드와 새 약점 집계 필드를 함께 보존해 해결했다. Claude의 main 기준 2프레임 보행 설명은 이 통합 브랜치의 나무·서리늑대 8단계 보행과 다르므로 이미 완료한 작업을 되돌리지 않는다. 쓰러짐 포즈·돌 갑옷병 보행은 별도 후속 후보이며 이번 포탑 단위에 섞지 않았다.

## 컨셉과 현재 모델의 차이

`art-source/defense/concepts/2026-10-29/props/six-tower-modules.png`의 포격탑은 원형 기초 위에 조준 가능한 상부가 놓인다. 기존 물폭탄포 모델은 이 구조에 황동 배관·청록 포신·물탱크를 더한 파생형이다. 전투에서는 정지 이미지를 좌우 반전하고 건물 전체를 흔들어, 위쪽 표적을 향한 발사 효과와 실제 포신의 방향이 어긋났다.

이번에는 Lv.2 물폭탄포의 물탱크·배관·압력계·포신을 `aim-platform` 관절 아래에 묶었다. 기초와 문장은 고정하고 상부만 8방향으로 조준한다. 포신은 별도 `barrel` 관절로 포강 축을 따라 뒤로 밀렸다가 복귀한다. 고정된 탱크를 포신이 가로지르는 구조를 피하려고 유압 장치 전체를 회전 상부에 넣었다. 기존 재료와 큰 실루엣을 유지한 관절 구조 개선이며 새 스킨 리그는 아니다.

최종 강화하면 다시 정지 이미지로 돌아가던 차이를 이어서 해결했다. Lv.3의 수정 왕관·궤도 링·물방울은 수조와 함께 회전하고, 기초 금테와 깃발은 고정한다. 금장 포구 끝을 별도로 투영해 발사 표시와 포탄이 강화된 포신에서 시작한다.

## 제작과 납품

```bash
npm run models:water-action
npm run models:water-action-lv3
blender --python-exit-code 1 -b --python tools/blender/build_water_cannon_action.py -- --check
blender --python-exit-code 1 -b --python tools/blender/build_water_cannon_action.py -- --level 3 --check
```

- 기준 원본: `art-source/defense/towers.blend` 보존.
- 새 편집 원본: `art-source/defense/water-cannon-action.blend`.
- 제작 코드: `tools/blender/build_water_cannon_action.py`.
- 실제 3D: `public/defense/models/water-cannon-action.glb`, 0.6초 `water-cannon-fire` 클립. 작업실의 기존 `?model=water-cannon` 항목에서 사용한다.
- 원본 렌더: `art-source/defense/water-cannon-action/`, 640px PNG 24개.
- 전투: `water-action-{0..7}-atlas.webp`, 각 1152×384, 준비·반동·복귀 3포즈. 합계 389,900바이트.
- 규격·해시: `public/defense/models/water-cannon-action.json`.
- 같은 카메라에서 계산한 포구 위치: `src/games/defense/waterCannonMuzzles.ts`도 제작 명령이 생성한다.

Lv.3 납품은 같은 구조의 `water-cannon-lv3-action.blend`, `water-cannon-lv3-action/` 원본 PNG 24개, `water-cannon-lv3-action.glb/.png/.json`, `water-lv3-action-{0..7}-atlas.webp`, `waterCannonLv3Muzzles.ts`다. 아틀라스 합계 492,350바이트, GLB 1,425,368바이트다. 작업실 `?model=water-cannon-lv3`에서 실제 발사 클립을 재생한다. 생성 JSON에 등급·재생성 명령·배율과 파일 해시를 기록한다. 기존 Lv.2 산출물은 덮어쓰지 않았다.

기존 카메라 `(9,-12,12)`, 목표 `(0,0,2.35)`, 정사영 배율 7.5와 지면 기준 약 `(320,488.648)`을 사용한다. 기존 자르기 영역 `(32,24,576,576)`을 384px 납품 이미지에 같은 비율로 적용한다. 포즈별 개별 확대·기초 반전은 하지 않는다. GLB는 약 1.24MB이며 전투에서는 다운로드하지 않는다.

## 전투 연결

Lv.2와 Lv.3 물폭탄포에 적용한다. 각 등급의 기본 렌더와 해당 아틀라스 8개가 모두 준비됐을 때만 그 등급의 동작을 사용한다. 일부 이미지 실패 시 해당 등급의 기존 렌더로 대체하며, 다른 등급의 로딩 성공 상태는 보존한다. Lv.3 기본 렌더도 실패하면 기존 Lv.2 정지 렌더를 사용한다. Lv.1과 다른 분기는 기존 외형을 유지한다.

Lv.2는 크기 100·배율 1.16, Lv.3는 크기 104·배율 1.16×1.025를 유지한다. 포구 좌표에도 같은 크기를 적용하되, Sprite의 하단 기준 0.1은 확대 배율과 구분한다. 두 등급의 기초 지면과 공통 카메라는 같고, 포즈별로 임의 재자르기하지 않는다.

조준은 엔진의 `tower.aim`을 따른다. 준비 중에는 장전 포즈를 유지하고, 실제 포탄이 생성돼 `recoil`이 설정된 뒤에만 포신을 뒤로 움직인다. 남은 반동 시간 0.12초를 기준으로 반동/복귀 포즈를 나눈다. 동작 줄이기에서는 장전 포즈를 유지하되 조준 방향과 발사 표시는 남긴다. 건설 때의 등장 연출은 유지한다.

섬광은 해당 포즈에서 투영한 포구에 표시한다. 포탄은 발사 직전 포구에서 출발해 원래 화면 궤적의 착탄점으로 이어진다. 화면 보정은 진행률에 따라 0으로 줄어들며 충돌 위치·피해·속도·범위는 바꾸지 않는다. 발사 당시 `sourceLevel`을 기록하므로 비행 중 강화/판매가 출발 위치를 바꾸지 않는다. 이전 저장 데이터에 이 필드가 없으면 기존 표시를 사용한다.

## 검증과 후속 범위

최종 전체 테스트 171개 중 170개 통과. 기존 수학 엔진의 `(3 × 7) ÷ 5` 정답 4/4.2 오류 1건은 남아 있다. 프로덕션 빌드 통과. 새 검사에서는 실제 발사 전 반동 없음, 일시정지, 강화/판매 후 발사 레벨 보존, 8방향 포즈·부분 로딩 실패, 화면 출발/착탄점과 입력 불변성을 확인한다.

Blender 원본을 다시 열어 Lv.2 기초 메시 99개와 Lv.3 고정 메시 108개의 행렬이 8방향 및 반동 단계에서 고정되는지, 포신이 조준 반대 방향으로 물러나고 정확히 복귀하는지 확인했다. GLB 재가져오기와 1개 translation 애니메이션 채널, 24원본 경계·8아틀라스 규격·파일 해시를 확인했다.

Chromium `http://localhost:3100/`의 1440×900·390×844에서 고정 상태 8방향×3포즈, 동작 줄이기와 이미지 실패 대체를 확인했다. 실제 UI로 3번 지점 건설 → 물폭탄포 강화 → 웨이브 보급 획득 → 최종 강화까지 진행했다. Lv.2와 Lv.3의 일시정지/재개 및 Lv.3의 1배속/2배속 발사를 확인했고 페이지 오류·가로 넘침은 없었다. 모바일은 확대 전환이 안정된 뒤 터치로 건설했다. 작업실은 실제 GLB 발사/복귀·메시 보기·동작 줄이기를 확인했다. 짧은 클립의 전후 이미지는 Playwright 시계를 고정해 비교하고 이후 시계를 재개했다. 작업실 측정은 Lv.2 29,946·Lv.3 34,170 삼각형이며 전투 GLB 비용이 아니다. Browser 실행 도구가 노출되지 않아 기존 Playwright/Chromium 검증을 사용했다.

전투는 계속 베이크 기반 2.5D이며 작업실만 실시간 3D다. 기존 3포즈를 방향별로 표시하므로 연속적인 포신 추적 회전은 후속 범위다. Lv.3 연결은 완료했다. 다음 우선 후보는 마을 건축과 입체 지형의 크기·조명·가림 비교다. 연속 추적 회전과 실제 Android GPU 성능은 별도 검증이 필요하다. 이번 회차는 예약 설정을 변경하지 않았고 Claude API를 사용하지 않았다.
