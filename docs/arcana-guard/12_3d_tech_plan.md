## 1. 3D 엔진 선택

### 1.1 비교

번들 크기는 minify+gzip 전송 크기 대략치. **[실측]** 표시는 `prototype/vendor/three.min.js`(REVISION 169 표기, IIFE 전체 빌드, 680,746B)를 gzip한 결과 약 174KB. 트리셰이킹 앱 번들은 이보다 작을 것으로 보지만 M1에서 Vite 최소 앱으로 재측정한다.

### 1.2 추천: Three.js

1. **번들 예산에 가장 맞는 "엔진 있는" 선택지**다. 완제품 엔진 중 트리셰이킹 후 크기가 가장 작고, 이미 실측한 전체 빌드조차 174KB다. Babylon·PlayCanvas는 이 숫자의 1.5~3배로 보이며, 06의 "엔진 0KB를 근거로 1.5MB 예산을 지킨다"는 기조를 3D에서도 가장 덜 해친다.
2. **필요한 기능이 딱 이 게임 크기다.** 필요한 것은 고정 직교 카메라, 정적 병합 메시, `InstancedMesh`, 정점 컬러 재질, 가산 빌보드, glTF 로더 정도이고 물리·씬 에디터·PBR 파이프라인은 필요 없다.
3. **로우폴리 glTF 파이프라인이 가장 표준적**이다. gltfpack(메시옵트 압축+양자화)·glTF-Transform·Blender 내보내기 조합의 사례와 문제 해결 자료가 가장 많다.
4. **허브 공존**: 06의 계약(엔진 중립)과 그대로 맞는다. Three는 `games/arcana-guard/render/three/` 안에서만 import하고, 허브 첫 화면에서는 로드하지 않는다. 다른 2D 게임은 이 청크를 존재조차 모른다.
5. **탈출구가 있다**: 어댑터 뒤에 두므로 Three가 틀린 선택으로 판명돼도 교체 범위는 `render/three/` 한 디렉터리다(1.4절).
6. **팀 리스크**: 문서·인력 시장이 가장 넓다. 단점인 잦은 마이너 릴리스(API 변경)는 **버전 고정 + 분기 1회 업그레이드**로 관리한다. 스파이크의 r169는 스파이크용이고, M2에서 그 시점 최신 안정판으로 고정해 번들 크기를 재측정한다.

WebGPU(Three의 `WebGPURenderer`)는 채택하지 않는다. 대상 기기(저사양 안드로이드·iOS 구버전)의 지원이 고르지 않고 번들이 늘어난다. WebGL2를 하한으로 두고 WebGL2가 없으면 2D 폴백으로 간다.

### 1.3 다른 후보를 쓰지 않는 이유

| 후보 | 탈락 이유 | 다시 볼 조건 |
|---|---|---|
| Babylon.js | 번들이 1.5~3배이고 기능(물리·GUI·노드 머티리얼·인스펙터)의 대부분을 쓰지 않는다. 저사양에서의 초기화·메모리 비용이 부담 | 에셋 파이프라인·씬 도구가 번들보다 중요해질 때(예: 3D 아티스트가 씬을 직접 조립) |
| PlayCanvas (엔진만) | 크기는 나쁘지 않으나, 엔진 단독 사용 사례·자료가 적고 팀 온보딩 비용이 큼. 장점(에디터)을 못 쓰는 구성 | 에디터 워크플로를 도입하기로 하면 재평가 |
| 직접 WebGL | 번들은 최소지만 glTF 로더·인스턴싱·컨텍스트 복구·셰이더 변형 관리를 전부 만들어야 해 수 주 소요, 기능 면에서 Three를 다시 만드는 셈 | 번들 예산이 Three 청크(약 150KB)조차 허용하지 못할 때 |

### 1.4 "렌더러만 교체" 탈출구 점검

**판정**: 탈출구는 성립한다. 단 **M2 안에서 선행조건 1~3을 충족**해야 하며, 그 전에는 "렌더러만 교체"가 말뿐이다. 프로토타입 `index.html`은 조건 1을 위반하므로(투영 섞인 px 거리) **이식 대상은 코드가 아니라 규칙**이다. 06 변경 제안 5("규칙을 `sim/` 형태로 이식 가능하게")는 3D 전환으로 더 중요해졌다.

### 2.2 게임 루프에서 3D가 추가하는 규칙

- **렌더 한 번에 `renderer.render` 한 번**. Three의 `setAnimationLoop`·`Clock`·`AnimationMixer`는 쓰지 않거나(영웅 스킨 애니메이션만 예외, 장식 시계) 06의 rAF 루프 안에서 호출한다. 루프는 하나다.
- 틱 사이에서 렌더는 `prev→curr` 선형 보간(위치, 각도는 최단호 보간). 30fps 상한 모드에서는 렌더 호출이 두 틱 사이에 3번 정도로 줄 뿐 시뮬은 그대로다.
- 정지 상태(일시정지·`visibilitychange`)에서는 rAF를 취소하고 GPU 작업이 0이 되게 한다. 드래프트 중 월드 ×0.3 슬로우는 시뮬 쪽 시간 배율이므로 렌더는 계속 돈다.
- 카메라 흔들림·번쩍임은 장식이며 `reducedMotion`이면 끈다(06 6.3, 08 A10).

### 2.3 허브 공존 체크

- 게임 진입 시 WebGL 컨텍스트 1개, 퇴장 시 `renderer.dispose()` + 지오메트리·재질·텍스처 dispose + `WEBGL_lose_context`로 명시 해제. 허브가 게임을 반복해서 열고 닫는 시나리오(20회)를 계약 테스트에 넣는다. 06의 "판 반복 10회 후 증가 < 10%" 기준을 그대로 적용한다.
- iOS Safari는 활성 WebGL 컨텍스트 수와 총 메모리에 민감하다(9절). 허브 자체는 WebGL을 쓰지 않는다.

### 2.4 성능 예산: 초기 로드 1.5MB를 3D에서 지킬 수 있는가

**질문**: 06 9.1의 "허브 첫 화면 → 첫 판 시작 가능, 전송량 기준 < 1.5MB"(그리고 M1의 "실측이 예산의 70% 이하")를 3D에서 지킬 수 있는가.

**항목별 추정(전송 gzip/brotli, KB)**

| 항목 | 06 (2D) | 3D 1단계(절차 생성, 에셋 0) | 3D 2단계(glTF 도입) | 근거 |
|---|---:|---:|---:|---|
| 허브+edu-core+ui+게임 코어 JS | 150 | 180 | 180 | 06 목표 150KB. 3D는 렌더 어댑터·지형 생성기·절차 모델 생성기가 +30KB [추정] |
| 3D 엔진 청크(Three 트리셰이킹+로더) | 0 | 150 | 200 (한도 230) | 전체 174KB [실측], 트리셰이킹 후 120~160 + GLTFLoader·메시옵트 |
| 3D 에셋(첫 스테이지분) | 240 (08의 아틀라스) | 0 | 320 (한도 400) | 5.2절 산출 |
| 오디오 필수분 | 300 | 300 | 300 | 06 유지 |
| 콘텐츠 팩 | 150 | 150 | 150 | 06 유지 |
| 폰트 서브셋+HTML/CSS/기타 | 100 | 100 | 100 | 06은 시스템 폰트 우선. 제목용 서브셋 포함 |
| **합계** | **940** | **880** | **1,250** | |
| 1.5MB 대비 | 63% | 59% | **83%** | |
| 2.0MB 대비 | — | 44% | **63%** | |

**판정**

- **1단계는 1.5MB를 지킨다**(59%, 06의 70% 규칙도 충족). 엔진이 +150KB지만 아틀라스 240KB가 사라지기 때문이다.
- **2단계는 "지킬 수는 있으나 여유가 없다"**. 83%로 70% 규칙을 못 맞추고, 추정 오차 ±30%를 곱하면 1.63MB로 상한을 넘는다. 즉 **1.5MB 상한은 측정 전부터 깨질 가능성이 높은 숫자**다. 여유를 만들려고 에셋을 깎으면 아트 방향이 예산에 끌려가게 된다.
- **그래서 상한을 올린다**: **초기 로드 < 2.0MB(상한), 목표선 1.4MB(70%)**. 2단계 추정 1.25MB는 목표선 안이고, 오차 +30%(1.63MB)도 상한 안이다.

**새 예산 (06 9.1 대체)**

| 항목 | 새 예산 | 비고 |
|---|---|---|

**상향의 근거와 완화책**

- 체감 비용: 저사양 4G 실효 약 4Mbps를 가정하면 1.5MB = 약 3초, 2.0MB = 약 4초, 목표선(1.4MB) = 약 2.8초 [추정]. 1판이 3~5분인 게임에서 **첫 진입 1회**의 +1초이고, 서비스 워커 캐시(06 M4) 이후 재방문 비용은 0이다.
- 허브 화면에 있는 동안 `requestIdleCallback`으로 게임 청크와 Three 청크를 **프리페치**(실행은 하지 않음)한다. `navigator.connection.saveData`가 켜져 있으면 프리페치하지 않는다.
- 압축은 brotli를 전제로 한다(정적 호스팅에서 사전 압축). gzip만 가능하면 위 숫자를 10~15% 높게 본다.
- 이 상향은 사용자 결정이 필요한 예산 변경이므로 `## 변경 제안` 2번에 올린다.

## 3. 렌더 아키텍처

### 3.1 계층

```
                       입력 액션 큐 {tick, action}
        ┌──────────────────────────────────────────────┐
        │                                              │
  ┌─────┴──────┐   hudState (값 바뀔 때만)        ┌─────┴───────────────────┐
  │  DOM UI    │◀─────────────────────────────── │  시뮬 코어 (sim/)         │
  │ 문제 카드   │                                  │  순수 TS · 타일 단위 좌표  │
  │ HUD·드래프트│                                  │  10틱/초 · 시드 RNG · SoA  │
  │ 슬롯 버튼   │                                  └─────┬───────────────────┘
  └─────▲──────┘                                        │ snapshot(prev, curr) + events
        │ slotRect / 투영 좌표                            ▼
        │                                  ┌─────────────────────────────────┐
        └──────────────────────────────────│  Renderer 인터페이스 (render/common)│
                                           │  draw(snapshot, alpha, events)   │
                                           │  pickTile · slotRect · resize     │
                                           │  setQuality · pause · dispose     │
                                           └───────┬───────────────┬─────────┘
                                                   ▼               ▼
                                         render/three/        render/canvas2d/
                                         (3D, 기본)            (폴백, 기능 동결)
```

의존 방향은 한 방향이다: `render/* → common`, `sim`은 아무것도 import하지 않는다(타입 제외). 시뮬은 렌더를 모르고, 렌더는 시뮬 상태를 **읽기만** 한다.

### 3.2 시뮬 코어 규칙 (3D로 인해 새로 못 박는 것)

1. **좌표는 평면 타일 단위 실수**. 타일 (c,r)은 [c,c+1)×[r,r+1), 중심은 (c+0.5, r+0.5). 사거리·속도·AoE 반경·길 길이 전부 타일 단위. px·고도 투영 오프셋 금지.
2. **고도는 정수 `elev`(0/1/2)만 시뮬이 안다.** 시뮬이 쓰는 것은 08의 규칙(사거리 배율, 저지대 소환 비용, 오르막/내리막 속도 배수)뿐이고 연속 높이는 모른다.
3. **사거리 판정은 평면 거리**. 타워가 더 높이 서 있어 보이는 것, 투사체가 포물선을 그리는 것은 렌더의 연출이다.
4. **경로는 타일 중심을 잇는 폴리라인**이고 적의 위치는 경로 진행 거리 `s`(타일)로 표현한다. `x,y`는 파생값이다. 렌더는 `s`를 받아 자기 경로 곡선(코너를 둥글게 깎은 스플라인)에 올린다.
5. **적끼리 충돌·밀어내기 없음**(타워 디펜스 관례). 적이 겹치는 것은 시뮬에서는 정상이고, 군중 모양은 렌더가 만든다(횡 오프셋, 7.3절).
6. **판정은 틱에서 확정, 투사체는 연출**: 발사 틱에 명중·피해를 확정하고, 눈에 보이는 투사체는 도착 시간만 연출한다. 대상이 먼저 죽어도 투사체는 마지막 위치로 날아간다. 이렇게 하면 투사체-적 충돌 검사가 0이 되고, 3D 포물선이 결과에 영향을 주지 못한다.
7. 엔티티는 **SoA 타입드 배열 + 고정 용량**(적 128, 투사체 128, 이벤트 256/틱)으로 두고 풀링한다. 틱 루프에서 객체를 만들지 않는다(06 6.3의 GC 규칙을 구조로 강제).

### 3.3 스냅샷 계약 (필드만, 코드 아님)

| 영역 | 필드 | 비고 |
|---|---|---|
| 공통 | `tick`, 이전/현재 이중 버퍼 | 렌더가 `alpha`로 보간 |
| 적 | `id`(런 안에서 재사용 금지), `kind`, `s`, `x`, `y`, `hpRatio`, `flags`(둔화·보호·방어 깎임·정예·보스) | 방향은 `s`의 경로 접선에서 렌더가 계산 |
| 타워 | `slotId`, `type`, `level`, `cooldownPhase`(0~1), `targetId` | |
| 투사체 | `id`, `kind`, 발사 위치, 도착 위치, 출발 틱, 도착 틱 | 연출 전용(3.2의 6) |
| 영웅(모드 플래그) | `x`, `y`, `state`(대기·이동·공격·스킬), `facing` | 영웅이 없는 수비 모드에서는 비어 있음 |
| 탑 | `hp`, `shield` | |
| 이벤트 큐(틱마다 비움) | `spawn`, `hit(targetId, kind)`, `kill(id, 위치)`, `leak(id)`, `summon(slot)`, `upgrade(slot)`, `ult(kind, 위치)`, `waveStart/End`, `levelUp` | 렌더 전용 소비. 이벤트에서 시뮬로 되돌아가는 경로는 없음 |

06의 `draw(snapshot, alpha)`는 **`draw(snapshot, alpha, events)`로 확장**한다(변경 제안 4). 이벤트는 파티클·피격 번쩍임·사운드 트리거에 쓰인다.

### 3.4 렌더 어댑터의 책임과 금지

| 책임 | 금지 |
|---|---|
| 지형·길·받침대·소품·적·타워·영웅·FX 그리기 | 게임플레이 타이머·난수 소유 (`Math.random` 금지는 렌더 장식에도 적용하되, 장식은 ID 해시로 결정적) |

| `pickTile`, `slotRect`, `resize`, `pause`, `dispose` | `sim/` 내부 구조 import (스냅샷 타입만 사용) |

### 3.5 문제 카드·HUD는 DOM으로 유지하는 이유

06의 결정(1.3의 5번)을 3D에서도 유지한다. 3D가 되면 근거가 오히려 강해진다.

1. **텍스트 품질**: 한글은 WebGL에서 SDF/비트맵 폰트 아틀라스가 필요해 한글 전체를 담으면 수백 KB~수 MB가 된다. 문제 지문은 매 문항이 바뀌는 임의 텍스트다. DOM은 시스템 폰트로 선명하게 그린다.
2. **IME·접근성**: 입력형 문항의 한글/영어 IME, 스크린 리더, 키보드(1~4키), 포커스 표시, 터치 타깃 44px는 DOM에서만 쉽다.
3. **렌더 부하와 입력 지연의 분리**: 3D는 GPU 부하에 따라 렌더 스케일(해상도)을 낮추고 30fps로 떨어질 수 있다. 문제 UI가 캔버스 안에 있으면 **글자가 같이 흐려지고 입력 피드백이 같이 느려진다.** DOM이면 3D가 흔들려도 입력 피드백 < 100ms(06)가 유지된다.
4. **반응형**: 세로/가로 전환(D13)과 `05_ui_ux_spec`의 레이아웃은 CSS로 처리한다. 캔버스는 "맵 영역" 컨테이너 크기만 따른다.
5. **주의 (3D에서 새로 생기는 규칙)**: 캔버스 위 DOM에 `backdrop-filter`·큰 블러·반투명 그림자를 쓰지 않는다(모바일 합성 비용이 큼). 비네트·색 등급 같은 화면 전체 효과는 정적 CSS 그라디언트 레이어로 처리한다. 캔버스에는 `contain` 계열 격리를 걸어 DOM 갱신이 캔버스 재배치를 일으키지 않게 한다.

**월드 안에서 그리는 것 / DOM으로 두는 것의 경계**

### 3.6 카메라: 직교 vs 원근 → **직교(고정)**

| 기준 | 직교 | 원근 |
|---|---|---|
| 타일 크기 일관성 | 화면 어디서나 같음 → 터치 타깃·사거리 원이 균일, 적 떼 크기 균일 | 원경이 작아져 아랫줄(가까운 쪽)과 윗줄 터치 목표 크기가 다름 |
| 맵 담기 계산 | 투영된 경계 상자의 닫힌 식(3.7절) | FOV·거리·기울기 3변수의 시행착오 |
| 슬롯 DOM 배지 위치 | 아핀 변환, 단순 | 비선형이지만 고정이라 가능. 다만 가장자리 왜곡 |
| 그림자·컬링·LOD | 그림자 맵 영역이 조밀, 거리 기반 LOD 불필요 | 적 떼 LOD/컬링 필요 |
| 로우폴리 미니어처 룩(레퍼런스) | 아이소메트릭/디오라마 느낌의 표준 | 깊이감은 더 좋으나 "하이퍼캐주얼 성 방어" 룩과는 다름 |
| 단점 | 깊이감이 약함(고도 단차가 정보가 됨) | — |

**결정: 직교, 고정 카메라**(회전·줌 없음, V-Follow의 자동 팬만 허용 — 13 §2.1). 원근을 쓰고 싶다면 FOV 12° 이하의 약한 원근(사실상 직교)을 M1 스파이크에서 A/B만 한다. 기본값은 직교다. <!-- v0.7 개정: FOV 15°→12°(13 §2.3 권고), "고정"의 뜻에 V-Follow 자동 팬을 명시 -->

- **피치(수평선 기준 내려다보는 각)**: **55° 고정**(13 §2.1: 50~60° 범위에서 한 값으로 확정, 단차 0.5T가 길 중심선을 가리지 않는 최저 피치는 50°). 피치가 높을수록 위에서 본 느낌이 강하고 세로 맵이 더 길게 보인다(3.7절 표). <!-- v0.7 개정: 기본 45°(조정 40~55°)→55° 고정, 브리프 §15 확정 -->
- **요**: 세로 화면 0°(맵 세로축이 화면 세로). 가로는 PC·태블릿 **요 45°(H45, 레퍼런스 룩)**, 폰 가로는 맵을 90° 눕혀(전치) **요 0°(H0)**. **45° 대각 요는 10×18 세로 맵에서 칸이 약 17px(13 §2.1, 스파이크 실측 16px)로 작아져 세로에서는 채택하지 않는다**(3.7절). 최종 룩은 13 문서가 정했고(2.1절), 요를 키우면 세로에서 칸이 작아지는 비용은 3.7절 표만큼 든다. <!-- v0.7 개정: 가로 요 90°→H45(요 45°)/H0(전치), 세로 45° 비용을 13 값(17px)으로 교체 -->
- **카메라 프리셋 4개**(13 §2.2): `V-Follow`(세로 폰 기본, 칸 34px, 18행 중 약 12.2행=68% 표시, 선두 적 행을 따라 세로로 팬, 슬롯 선택 시 0.3초 팬), `V-Fit`(맵 영역을 길게 누르는 동안 전체 보기, 칸 21px), `H45`(PC·태블릿 가로), `H0`(폰 가로). 같은 장면을 쓰고 카메라 값·UI 안전영역만 다르다. <!-- v0.7 개정: 브리프 §13 D13 잠정 채택(세로 요 0° 추적 카메라, 칸 34px, 길게 누르면 전체 보기) 반영 -->
- 카메라 파라미터(피치·요·줌 여백)는 한 곳의 설정값이고, 맵 데이터·시뮬은 카메라를 모른다.
- **가림(오클루전)**: 카메라가 남쪽에서 북쪽을 보므로 높은 타일이 북쪽(뒤) 타일을 가린다. 인접 고도 차 ≤ 1(08)이면 가려지는 길이는 `(단차 0.5 + 파임 0.08) ÷ tan(피치)` ≈ 0.41칸(피치 55°)이고, 적이 지나는 중심선(칸 중앙, 0.5칸 지점)은 가려지지 않는다(13 §3.1; 일반식 `단차 ≤ 0.5·tan(피치) − 0.08` → 55°에서 0.63T 이하). 길 남쪽에 한 단 높은 이웃이 있는 칸에서는 길의 남쪽 41%가 앞면에 가려지므로 적 HP 바는 몸이 가려져도 보이게 한다(13 §3.1·§8.2). <!-- v0.7 개정: 가림 식을 단차 0.5T·파임 0.08T·피치 55° 기준으로 교체(13 §3.1) --> 규칙은 4.7절의 맵 린트로 강제한다.

### 3.7 10×18 맵을 화면에 담기 (D13 잠정 채택: 세로 우선 + 요 0° 추적 카메라, 가로 요 45°) <!-- v0.7 개정: 브리프 §13 D13 잠정 채택 반영 -->

**공통 원리**: 맵의 투영 크기를 닫힌 식으로 구해 영역에 맞춘다. `고도 단위 H = 0.5타일/단계`, 위쪽 여유(타워·정예 높이) 1.2타일, 최대 고도 2단계(1.0타일)를 반영하면, <!-- v0.7 개정: 0.45→0.5, 0.9→1.0(브리프 §15 단차 0.5T) -->

- 요 0°: 투영 폭 = 10, 투영 높이 = `18·sin(피치) + 2.2·cos(피치)` (타일 단위, 2.2 = 여유 1.2 + 최대 고도 1.0) <!-- v0.7 개정: 2.1→2.2, 이 식이 13 §2.1 표(45° 23.8px / 55° 21.2px)를 재현함 -->
- 가로 전치 H0(맵 90° 회전 + 요 0°): 투영 폭 = 18, 투영 높이 = `10·sin(피치) + 2.2·cos(피치)` <!-- v0.7 개정: 요 90° 식을 H0로 개칭, 2.1→2.2, 여백 1 제거(13 §2.2의 H0 544×314→30px와 일치) -->
- 요 45°(H45): 투영 폭 = (10+18)/√2 ≈ 19.8, 투영 높이 = `19.8·sin(피치) + 2.2·cos(피치)` <!-- v0.7 개정: H45 식 추가(13 §2.2의 PC 880×600→34px, 폰 544×314→18px 재현) -->

캔버스는 **전체 화면이 아니라 맵 영역 컨테이너 크기**로 만든다. 문제 카드 영역까지 렌더하면 픽셀의 30~40%를 낭비한다. 방향이 바뀌면 카메라 요와 컨테이너 크기만 바꾸고 시뮬·맵 데이터는 그대로다(3D의 이점).

### 4.1 입력과 원칙

### 4.2 고도 0/1/2 → 하이트맵 메시 (계단형 절벽)

타일 상면을 평평한 면으로 두고 높이가 다른 이웃 사이는 수직 벽으로 잇는 **테라스(계단) 방식**이다. 부드러운 경사 지형보다 레퍼런스의 "절벽 단차" 룩에 맞고, 정점 수가 적다.

1. **정점 격자**: 코너 격자 11×19에 시드 기반 결정적 지터(XZ ±0.06타일)를 준다. 모든 타일이 같은 코너 XZ를 공유하므로 이웃 타일 사이에 틈이 없다. 지터가 있어 칸 격자가 기계적으로 보이지 않는다.
2. **상면**: 타일 높이 = `elev × 0.5타일`(상수 `H_LVL`, 렌더 전용). 상면 정점에 ±0.02 이하의 미세 높이 잡음(길 위에서는 0). 길 타일은 같은 고도 지면보다 0.08타일 낮춘다(4.3절). <!-- v0.7 개정: 단차 0.45→0.5T, 파인 길 0.08T 연결(브리프 §15, 13 §3.1) -->
3. **절벽 벽**: 타일 변의 이웃이 더 낮으면 그 변에 수직 벽 2삼각형. 08이 인접 고도 차 ≤ 1을 보장하므로 벽 높이는 항상 0.5타일 한 단이다(맵 가장자리 스커트와 길 둑 벽 제외). 벽 윗단에 0.06타일 폭의 안쪽 모따기(립)를 한 줄 더 넣으면 입체감이 크게 늘고 비용은 변당 2삼각형이다(품질 사다리 상위에서만). <!-- v0.7 개정: 벽 높이 0.45→0.5타일(13 §3.1), 길 둑 벽 0.08타일은 4.3절 -->
4. **맵 가장자리 스커트**: 바깥으로 −0.6타일까지 내려가는 벽 4면(기저 단). 장식 링(2칸)은 별도 저폴리 조각.
5. **병합**: 상면·벽·스커트·파인 길을 **하나의 `BufferGeometry`**로 합친다. 재질 1개, 드로우콜 1. <!-- v0.7 개정: 길 리본 별도 메시 폐기에 따라 파인 길을 병합 대상에 포함(13 §3.1) -->
6. **규모(추정)**: 상면 180타일 × 2삼각형 = 360, 벽 최대 약 100변 × 2 = 200, 길 둑 벽 최대 약 75변(길 약 37타일 × 양쪽) × 2 = 150, 스커트 약 110, 장식 링 약 150 → **약 1.0k~1.2k 삼각형**. 플랫 셰이딩을 위해 정점 복제를 해도 약 3k 정점이다. <!-- v0.7 개정: 파인 길 둑 벽 추가로 0.8k~1k→1.0k~1.2k(추정). 13 §1.1의 지형 상한 6,000삼각형(스커트 포함) 안 -->

### 4.3 길 메시 (파인 길) <!-- v0.7 개정: 길 리본→파인 길(브리프 §15, 13 §3.1) -->

- **램프**: 시뮬의 오르막/내리막 규칙(08: 칸에 들어설 때 고도가 변함)을 눈에 보이게 하는 부분이다. 연속한 두 길 타일 사이의 공유 변 높이를 **두 타일 고도의 평균**으로 정하고, 길 타일 상면은 입구 변↔출구 변 사이를 선형 보간한다(코너 타일은 중심을 자기 고도로 두는 삼각형 부채). 이웃과 변 높이가 일치하므로 틈이 없다.
- 시뮬은 "들어선 칸에 속도 배수를 적용"하고 렌더 램프는 경계 양쪽 반 칸에 걸쳐 있어 최대 반 칸 어긋난다. 눈에 띄지 않는 오차로 보고 허용한다(적의 높이는 아래 `pathHeight`로 구해 램프를 정확히 타므로 시각적 위화감은 없다).
- **파인 길**: 길 타일의 윗면을 같은 고도 지면보다 **0.08타일 낮춘다**(지면 위에 띠를 올리는 리본 방식은 폐기). 파임 가장자리에 0.08타일 높이의 둑 벽이 서고, 가장자리 정점 컬러를 −12% 어둡게 해 길을 한 줄 윤곽으로 읽히게 한다. 길은 흙색(13 M3), 정점 컬러에 약한 얼룩 잡음. 별도 메시가 아니라 지형 병합 메시(4.2절)의 일부라 폴리곤 오프셋이 필요 없고, 삼각형은 4.2절 #6에 포함된다(구 리본 약 900삼각형 삭제). <!-- v0.7 개정: 리본(지면 위 +0.03T, 폭 0.8타일, 약 900삼각형)을 파인 길 0.08T로 교체(브리프 §15, 13 §3.1) -->
- **`pathHeight(s)`**: 경로 진행 거리 `s` → 지면 높이를 0.25타일 간격으로 미리 구운 표. 적·영웅의 Y를 구할 때 레이캐스트 없이 표 조회와 보간만 쓴다.
- **`s` → 곡선 위치 매핑**: 시뮬 경로(직각 코너)와 렌더 곡선(둥근 코너)은 길이가 약 3~4% 다르다(코너 6개 × 약 0.2타일 단축). 코너 사이 구간별 정규화 테이블로 `s`를 곡선 위 위치·접선으로 바꾼다. 방향(yaw)은 접선에서 나온다.
- **길 폭**: 파인 길은 칸 전체가 파이므로 시각 폭이 1.0타일이다(0.8타일 리본과 1.0타일 확장 옵션은 폐기). 적 떼(7절)의 횡 오프셋 ±0.25타일이 길 안에 들어간다(시뮬 판정은 중심선 기준이라 영향 없음). <!-- v0.7 개정: 시각 폭 0.8→1.0타일 고정(파인 길은 타일 단위, 13 §3.1·§6.2) -->

### 4.4 슬롯 받침대 ("고정 건설 터")

- 받침대 = 8각 기둥 단 쌓기(13 §3.3): 바닥 지름 0.9타일·윗판 지름 0.78타일, 높이는 저(1단) 0.14 / 중(2단) 0.28 / 고(3단) 0.42타일, 단마다 안쪽으로 들어가고 모서리에 챔퍼. 상판은 비어 있을 때 **구매 가능/불가 색**을 인스턴스 색으로 표시한다. <!-- v0.7 개정: 반지름 0.42·높이 0.18타일을 13 §3.3의 지름·단별 높이로 교체 -->
- **고도 표시를 색에만 의존하지 않는다**(08 A8, 2.4): 08의 문양 ○/^/^^ 에 해당하는 것으로 받침대 **돌 단 수 1/2/3단**(저/중/고)을 쓴다. 지형 높이가 이미 다르지만 단 수가 같은 규칙을 한 번 더 말해 준다.

- 선택 시 사거리 링은 **지형 보너스가 반영된 반지름**(×1.00/1.08/1.15)을 지면 데칼로 그린다(08 2.4와 동일 정보, 평면 거리 기준이므로 타원이 아니라 원이 지면에 놓여 직교 카메라에서 균일한 타원으로 보임).
- 타워(수호자)는 받침대 위에 놓는 모델이고 레벨마다 형태가 바뀐다(5절).

### 4.5 굽기: 색·그림자·난이도 등급

정점 컬러에 다음을 한 번에 굽는다(스테이지 진입 시 1회, 캐시 키 `${R}-${S}-${D}`, 동시 최대 2세트 — 08과 동일).

1. 지면 A/B 두 색을 타일 해시로 번갈아(08 R 파라미터 표).
2. 고도 +1마다 상면 밝기 +4%(08 4.3).
3. **고정 광원 기준 면 음영**: 광원 방향 하나를 정해 면마다 `max(0, N·L)`을 곱한 값을 굽는다. 벽은 상면보다 10~24% 어둡게(08 4.3의 절벽색 규칙).
4. **AO 비슷한 접촉 그림자**: 더 높은 이웃과 맞닿는 코너 정점을 어둡게(알파 0.24 상당), 낮은 이웃 쪽 변에 밝은 립(알파 0.30 상당)(08 4.3 값 재사용).
5. **난이도 등급 `grade(D)`**: 08 1.2의 식(`mix(색, D.tint, D.amt) × D.bright`, 채도 상한 0.48)을 정점 컬러에 적용. 이 함수는 순수 색 계산이라 `render/common/theme`에서 2D/3D가 공유한다.
6. 결과: 지형은 **라이트 계산이 없는 Basic 계열 재질 + 정점 컬러** + 안개로 그린다 → 저사양에서 프래그먼트 비용이 최소다. 움직이는 객체(적·타워·영웅)만 Lambert 계열 재질 + 방향광 1 + 반구광 1을 쓴다.

## 5. 에셋 전략

### 5.1 1단계: 절차 생성 (프리미티브 + 정점 컬러, 에셋 0KB)

M2~M4까지 쓰는 기본 경로다. 모델은 코드가 만드는 저폴리 조합이고, 파일은 하나도 내려받지 않는다. 이 단계에서 파이프라인(인스턴싱·팔레트·예산)을 모두 확정한다.

| 대상 | 절차 모델(예) | 삼각형 |
|---|---|---:|
| 안개 조각 | 둥근 덩어리(20면체 변형) + 점 눈 2개 | 약 120 |
| 속삭임 | 늘어난 8면체 + 꼬리 쐐기 | 약 100 |
| 침묵 덩어리(정예) | 각진 12면체 + 받침 | 약 160 |
| 망각의 왕(보스) | 겹친 덩어리 + 왕관 | 약 400 |
| 수호자 4속성 × Lv1~4 (16종) | 완드: 원뿔+구(불꽃) / 컵: 원통+토러스 / 소드: 얇은 상자 3개 / 펜타클: 낮은 5각 기둥. 레벨 = 크기·고리·장식 추가 | 150~600 |
| 받침대·탑·안개 문 | 8각 프리즘, 적층 원통+원뿔+발광 구, 토러스+가산 | 각 100~500 |
| 영웅(영웅/RTS 모드) | 캡슐+구+지팡이, 절차 흔들림 애니메이션 | 약 250 |
| 투사체·파티클 | 다이아몬드·구, 가산 빌보드 | 8~20 |

- 애니메이션은 **셰이더 기반 절차 애니메이션**: 걷는 상하 흔들림·눌림은 인스턴스 ID와 시간으로 정점 셰이더에서 계산한다(CPU 0, 적 떼 전원이 공짜). 처치는 인스턴스 스케일 축소 + 가산 빌보드 번쩍임(폭력 표현 없이 "흩어짐", 00 2절).
- 외곽선(08 A7의 흰 외곽선 번역)은 **반전 헐 2패스**가 정석이나 인스턴스 비용이 2배가 되므로 품질 사다리 최상(Level 0)에서 정예·보스·영웅에만 쓴다. 나머지는 몸통 밝기 + 접지 그림자 원판(인스턴스)으로 분리한다. 08 A3(길↔적 대비 ≥ 3:1)는 **3D 렌더 스크린샷의 픽셀 측정**으로 재검증한다(`bg_test.js` 방식 재사용). 조명이 들어간 색은 팔레트 값과 다르기 때문이다.

### 5.2 2단계: 로우폴리 glTF (아트 교체)

절차 모델을 같은 슬롯(이름·피벗·크기)에 glTF로 하나씩 갈아 끼운다. 지형·길·받침대 메시 생성은 계속 코드가 담당한다.

**에셋 수와 크기 추정**

| 묶음 | 개수 | 개당 삼각형 | 개당 크기(양자화+메시옵트, 전송) | 합계 | 로드 시점 |
|---|---:|---:|---:|---:|---|
| 적 | 4종 (+ 저폴리 LOD 4) | 150~800 | 3~7KB | 약 30KB | 공통 |
| 수호자 | 16종 | 400~1,500 | 6~12KB | 약 130KB | 공통 |
| 받침대 | 3종 | 200~400 | 2~3KB | 약 8KB | 공통 |
| 탑·안개 문 | 지역별 4+4종 | 1,000~2,500 | 8~25KB | 약 120KB | 지역 단위 |
| 과목 소품 | 4세트 × 5~6종 | 100~600 | 2~4KB | 세트당 약 18KB | 과목 단위 |
| 지역 데코 | 4세트 × 8종 | 50~300 | 1~2KB | 세트당 약 12KB | 지역 단위 |

| 팔레트 텍스처(공용) | 1~2 | 128² | 1~3KB | 약 5KB | 공통 |
| **전체 합계** | 약 100개 조각 / 파일 약 20개 | | | **약 600KB** | |
| **한 스테이지 로드분** | | | | 공통 175 + 지역(탑·문·데코·원경 약 80) + 과목(약 18) + 영웅(해당 시 50) = **약 270~320KB** | 한도 400KB |

- 추정 근거: 인덱스 정점 한 개당 약 8~10바이트(양자화 위치+법선+컬러) × 정점 수(삼각형의 약 0.6배), 메시옵트+brotli로 추가 40~50% 감소. 첫 스테이지분 한도 400KB 안에 들어가며 2.4절의 합계(320KB)와 일치한다.
- 아티스트가 필요한 **고유 모델 수**는 색·크기 변형(정점 컬러/팔레트로 해결)을 빼면 약 60개다. 9절 리스크 참조.

**압축 선택**

| 방식 | 판단 |
|---|---|
| **메시옵트(gltfpack) + 양자화** | **채택.** 디코더가 수 KB 수준이고 모델이 작아도 이득이 있다 |
| Draco | **채택하지 않음.** 디코더(wasm) 100KB급이 모델 600KB 전체의 이득보다 큼. 모델이 2k 삼각형 이하라 압축 이득이 작다 |
| KTX2/Basis 텍스처 | **채택하지 않음.** 텍스처가 128² 팔레트 1~2장 → PNG/WebP로 충분. 트랜스코더(200KB+)가 이득보다 큼. 텍스처가 256² 아틀라스 이상으로 커질 때만 재평가 |
| 정점 컬러 대신 팔레트 텍스처 | 컬러 변형이 필요한 모델은 팔레트 UV 한 점 샘플링 방식(텍스처 1장 공유). 인스턴싱에서 재질 1개로 유지되는 이점 |

**파이프라인**: Blender(또는 외부 키트) → glTF/GLB 내보내기 → CI에서 gltfpack 압축 + glTF-Transform으로 dedupe/prune + glTF 검증기 → `assets/models/` 산출. 삼각형·크기 예산 초과 시 빌드 실패. 외부 에셋은 **CC0 또는 상업 이용 가능 라이선스만**, 출처·라이선스를 `assets/LICENSES`에 기록한다. 생성형 3D 도구 결과물은 토폴로지·라이선스 검수 비용이 커서 기본 경로로 삼지 않는다.

### 5.3 적 떼: InstancedMesh

- **종류별 InstancedMesh 1개**(적 4종 → 드로우콜 4). 용량은 시뮬 용량과 같은 128. `mesh.count`를 살아 있는 수로 조정하고 `frustumCulled`는 끈다(경로 전체가 화면 안).
- 인스턴스 행렬은 **Float32Array에 직접 기록**한다(`Object3D.updateMatrix` 경유 금지). 위치(Y는 `pathHeight`), yaw, 스케일(처치 연출), 횡 오프셋(7.3절)을 합성한다. 50마리 × 64바이트 = 3.2KB/프레임 업로드이고 CPU는 0.1ms 미만 [추정].
- 인스턴스별 속성 2개(둔화·피격·보호 상태 틴트, 보행 위상)를 `InstancedBufferAttribute`로. 걷기 흔들림·피격 번쩍임은 정점/프래그먼트 셰이더에서 처리한다. 커스텀 셰이더는 **재질 2종 이하**로 제한(`onBeforeCompile` 확장은 Three 업그레이드 때 깨지기 쉬움).
- **개체 수 LOD**: 개체 하나하나의 거리 LOD가 아니라 *살아 있는 수가 30을 넘으면 저폴리 메시로 일괄 교체*하는 방식(직교 카메라라 거리 LOD는 의미 없음).
- 정예·보스·영웅은 인스턴스가 아닌 **개별 메시**(HP 바·외곽선·스킨 애니메이션 허용).
- 투사체도 InstancedMesh 1개(용량 128), 파티클은 `Points` 1개(고정 크기 링 버퍼 ≤ 150, 품질 사다리로 감소), 그림자 원판(blob)도 인스턴스 1개.

## 6. 성능 예산과 측정 계획

06 9.2의 기준 기기는 "RAM 2~3GB, A53급"이었다. 3D에서는 **기준 기기를 올리고, 그 아래는 2D 폴백이 담당**한다. 이 분리가 3D 예산을 현실적으로 만든다.

### 6.1 목표 기기와 티어

| 티어 | 대표 | 3D 지원 | 기본 품질 |

| **L (3D 하한, 측정 기준 기기)** | **2019년형 중저가 안드로이드, RAM 4GB**, Mali-G72/Adreno 5xx급(예: Galaxy A50, Redmi Note 7급. 구체 모델은 M1에서 2종 확정: Mali 1, Adreno 1), Android Chrome 최신-2 | O | Level 2 → 필요 시 Level 3 |

| H | 최신 플래그십, A15 이상, PC 내장 GPU 이상 | O | Level 0 |

### 6.4 열 쓰로틀링 대응 (30fps 상한 모드)

3~5분 판을 하루 2~3번 연속하면 저사양 기기는 3~5분 지속 GPU 부하에서 클럭이 떨어질 수 있다(브리프의 "하루 10~15분"). 전략은 **측정 → 사다리 하강 → 30fps 상한 → 폴백 제안** 순서다.

1. **감시**: 렌더 프레임 시간의 최근 3초 p95. 06 6.3의 규칙(> 20ms)을 그대로 쓴다.
2. **하강**: p95 > 20ms가 3초 지속되면 Level을 한 칸 내린다. 한 번 내리면 **6초 동안 재평가하지 않고**(오스실레이션 방지) 한 판 안에서는 **다시 올리지 않는다**. 다음 판 시작 때 이전 판의 80% 프레임이 12ms 이하였으면 한 칸 올려서 시작한다.
3. **Level 3 = 30fps 상한**: rAF 콜백을 건너뛰어 렌더를 격프레임 이상으로 줄인다(60Hz에서 2프레임당 1회, 90/120Hz에서는 3~4프레임당 1회). 시뮬은 10틱 고정이므로 게임플레이는 동일하고 보간 렌더라 체감도 크게 다르지 않다. `lowPowerMode: "on"`이면 처음부터 Level 3. 90/120Hz 화면에서도 기본 상한은 60fps다.
4. **Level 3에서도 p95 > 33ms가 지속되면** 판 도중에는 바꾸지 않고(시각적 불연속) 결과 화면에서 "화면을 단순하게 바꿀까요?"로 2D 폴백을 제안한다. 단, 컨텍스트가 복구 불가하게 소실되면(`webglcontextlost` 후 복구 실패) 즉시 일시정지 → 2D 전환 → 안내 토스트.
5. **iOS 저전력 모드**는 Safari가 rAF를 30fps로 제한하는 것으로 알려져 있다(실기기 확인 필요). 30fps 설계가 이를 그대로 흡수한다.
6. 일시정지·탭 숨김 시 렌더 완전 정지(GPU 0), 오디오 `suspend()`는 06 그대로.
7. 열 상태는 브라우저 API로 읽지 않는다(안정적 API 없음). 프레임 시간 추세가 대리 지표다.

### 7.2 결론

- **D11은 아키텍처를 바꾸지 않는다.** 시뮬 SoA 용량 128, 종류별 InstancedMesh, 이벤트 큐, 개체 수 LOD, 처치 연출 병합은 **D11과 무관하게 M2에 구현**한다. 50마리 기준으로 짜 두면 5마리는 공짜다.
- D11에 따라 달라지는 것은 ① 에셋의 폴리 수·수량과 애니메이션 방식 ② 연출 방식(개별 vs 군중) ③ 밸런스 문서의 수치 ④ 가독성 UI(HP 바 정책)이다. 기술 리스크는 소수 정예가 약간 낮고(저사양 부담 ↓), 다수 떼는 레퍼런스 룩에 가깝다. **기술은 어느 쪽이든 막지 않는다.**
- 스파이크 M1에서 5/25/50/100 토글로 실측하여 이 표를 확정한다.
