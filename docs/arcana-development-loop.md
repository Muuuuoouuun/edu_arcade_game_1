# 아르카나 개발·자가 점검 반복 운영

기준일: 2026-11-01 (Asia/Seoul). **1시간마다 시작하는 점검·개발 주기**의 실행 규약이다. 이 문서 작성만으로 예약 실행이 등록되지는 않는다. 예약 상태·다음 실행 시각은 실제 스케줄 도구의 결과로 확인하고, 실행 수단이 없으면 상시 자동 운영 중이라고 표시하지 않는다.

## 목표와 범위

우선순위는 **오락성 → 그래픽 → 최소 교육**이다. 기획자 관점에서 “다음 한 판을 하고 싶은가, 무엇을 바꾸면 판단과 액션이 더 재미있어지는가”를 먼저 묻는다. 기능 개수나 코드 변경량을 성과로 삼지 않는다.

사용자의 최신 지시(2026-11-01)에 따라 **기획·게임성·디자인·모델링·구조/로직·모바일 완성도**를 함께 발전시킨다. 매 회차 여섯 분야의 상태를 짧게 점검하고, 한 분야의 구현·검증 가능한 개선 하나를 완료한다. 완료한 회차마다 기획 → 게임성 → 디자인 → 모델링 → 구조/로직 → 모바일 순서로 주 분야를 옮긴다. 미완료 소유 작업과 확인된 오류는 우선 처리하고 순서를 바꾼 이유를 기록한다. 모델링은 계속 반복하되 타워 분기만 연속 제작하지 않는다.

[모바일 게임 품질 로드맵](arcana-mobile-quality-roadmap.md)의 참고작·수용 기준을 따른다. 준비 화면은 컨셉 아트와 이미지 중심, 스테이지는 별도 전투 화면으로 유지한다. 허브의 수학·단어·상식·카트 진입과 기록, 디펜스의 최소 교육 원칙을 보존한다. 별도 3D 수학 카드 실험을 원정 캠페인과 합치지 않는다.

## 한 주기의 실행 순서

한 주기는 40~45분을 목표로 최대 50분 안에 마치고 다음 시작까지 여유를 둔다. 이전 주기가 실행 중이면 새 개발 작업을 겹쳐 시작하지 않는다. 진행 상태와 담당자를 확인해 기존 작업을 이어가거나 이번 시작을 건너뛰며 이유를 기록한다.

새 작업 브랜치를 만든 즉시 소스 편집 전에 해당 주기의 증거 폴더에 `summary.md`를 만든다. 실행 ID·KST 시각, 이 루프가 소유한 브랜치, 기준·현재 HEAD SHA, 한정된 범위(미선정이면 선정 대기), **미완료** 상태, 미커밋 파일과 남은 검증을 기록한다. 검증한 기준·head SHA는 실제 검사 전까지 **미검증**으로 표시한다. 작업 선택 후 편집 전에 범위·수용 기준을 확정하고, 구현·검증·커밋·PR 단계마다 같은 기록을 갱신한다. 마지막 턴까지 기록을 미루지 않는다. 중단된 작업의 소유권은 `codex/arcana-loop-*` 브랜치와 이전 기록의 명시적 소유 선언을 함께 확인하며, 초기 미완료 기록도 근거로 인정한다. 차단 보고서가 브랜치 이름을 언급한 것만으로 소유권을 인정하지 않는다. 복구용 기록은 테스트·리뷰·병합 성공의 증거가 아니며 기존 검증·병합 조건은 그대로 적용한다.

| 구간 | 실행 | 완료 조건 |
| --- | --- | --- |
| 0~5분 | 작업 트리·브랜치·원격 main·열린 PR·다른 세션 진행을 확인한다. 원격을 fetch하고 마지막 점검 이후 변경을 읽는다. | 기준 커밋, 미커밋 작업 소유자, 합칠 작업과 보존할 작업이 확인됨 |
| 5~10분 | PC·모바일의 실제 게임과 해당 모델·시안을 비교하고 여섯 분야의 상태와 문제를 기록한다. 이번 주 분야에서 가치가 높은 **한 단위**를 선택한다. | 기준 증거, 개선 가설, 전후 비교 지표, 이번 범위가 한 문단으로 정해짐 |
| 10~30분 | 해당 분야의 구현과 독립 검증을 필요한 역할에 나눠 진행한다. 같은 파일의 편집 책임자는 한 명으로 둔다. | 편집 가능한 원본·재현 가능한 산출물과 게임에서 보이는 변경이 생김 |
| 30~42분 | 변경에 맞는 자동 검사와 실제 브라우저 조작을 수행한다. 같은 조건의 전후 화면·전투 결과를 비교하고 결함을 고친다. | 수용 기준 충족, 새로운 오류 없음, 증거와 한계 기록 |
| 42~45분 | 원격 main을 다시 확인하고 병합 또는 PR을 마무리한다. 기획 판단과 다음 후보를 남긴다. | 반영 커밋/PR, 검증 결과, 다음 작업이 명확함 |

45분까지 결과 또는 인계를 기록하고 종료한다. 50분 강제 제한까지의 마지막 5분은 프로세스 정리 여유이며 새 작업에 쓰지 않는다. 시간을 넘길 것으로 보이면 범위를 줄이거나 진행 중 브랜치·재현 방법·남은 검증을 인계한다. 시간이 다 됐다는 이유로 실패한 코드를 main에 넣지 않는다. 후보가 너무 크면 전체 카메라 개편 대신 한 모델의 실루엣이나 한 동작처럼 검증 가능한 시각 단위로 줄인다. 그래도 개선 가치가 확인되지 않거나 필요한 도구가 막혔으면 근거와 미완 원인을 기록하고 변경 없이 종료한다. 동일한 화면을 명분 없이 다시 꾸미거나 빈 커밋을 만들지 않는다.

## 기획자가 고를 기준

1. **게임성:** 플레이어가 선택할 이유가 있는가? 강한 조합과 약한 조합의 결과가 보이는가? 실패 후 바꿀 행동을 알 수 있는가?
2. **그래픽:** 시안의 특징이 작은 화면에서도 남는가? 길·적·영웅·공격 예고가 장식보다 먼저 보이는가? 움직임이 공격 시점과 실제 판정에 맞는가?
3. **교육:** 전술에 쓸 작은 원리만 남겼는가? 전장 규칙과 자연의 원리를 구분했는가? 읽지 않아도 다음 전투와 보상을 받을 수 있는가?
4. **범위:** 한 주기에 검증할 수 있는가? 다른 세션의 변화와 중복되거나 현재 저장·입력·진행을 흔들지 않는가?

수용 기준은 구현 전에 정한다. 예를 들어 “390px 전장에서 화염탑의 코어와 석재를 구분하고 인접 건설 지점을 가리지 않는다”, “발리스타의 장전·발사에서 탄과 활대가 잘리지 않고 같은 접지점을 유지한다”, “물폭탄포 GLB와 전투 렌더에 같은 탱크·배관 구조가 나타난다”처럼 관찰할 수 있게 쓴다. 재미와 교육 효과는 자동 테스트만으로 입증했다고 쓰지 않는다.

## 그래픽·모델링 제작 규칙

- 기존 타워 제작 경로는 `tools/blender/build_towers.py` → `art-source/defense/towers.blend` 및 `public/defense/models/`의 GLB·투명 PNG·manifest다. `npm run models:build`는 이후 `tools/build-tower-sprites.mjs`로 같은 640px 캔버스의 `*-game.webp`·`game-sprites.json`도 갱신한다. 전투에서는 이 WebP를 사용하며 PNG는 원본 렌더로 보존한다. `src/model-lab.ts`의 3D 모델실과 `src/games/defense/art.ts`의 전투 에셋 선택을 함께 확인한다. 현재 커밋에서 실제로 연결된 자산을 읽고 이미 완료된 개선을 반복하지 않는다.
- GLB 지오메트리를 회전하는 **실제 3D**, Blender로 렌더해 전투에 쓰는 **2.5D 스프라이트**, SVG 성문과 콘셉트 일러스트를 구분한다. 모델링을 했다고 보고할 때는 형태나 구조 변경을 포함한다. 효율적인 전투 스프라이트를 바꾸기 위해 각 유닛에 실시간 3D 렌더러를 추가하지 않는다.
- 작은 화면에서 읽히는 큰 형태와 스타일의 일관성을 먼저 만든다. 미세 장식 수만 늘리지 않는다. 재질 경계·무기 실루엣·포신 깊이·코어 밝기가 실제 게임 크기에서도 남는지 본다. 접지점, 포즈 크기, 좌우 방향, 반동·발사 시점, 길·건설 지점의 가시성과 조작을 보존한다.
- 편집 원본과 재현 명령을 남기고 기존 `fire-core`·`turret`·`bolt`·`barrel` 애니메이션 노드 계약을 관련 모델에서 유지한다. 일부 모델만 생성하는 옵션을 썼다면 최종 manifest가 다른 모델 항목을 지우지 않았는지 확인한다. 현재 설치된 Blender·렌더 도구를 먼저 활용한다.
- 산출물은 모델실의 확대 이미지로 끝내지 않는다. 실제 전투에서 해당 건설·강화 외형을 띄우고, 전후 같은 카메라·뷰포트·스테이지·강화·동작 단계로 비교한다. 에셋 로드 실패 시 대체 표시도 영향을 받으면 검증한다.

## 다른 세션과 Claude 5.5 사용

| 역할 | 사용 시점 | 산출물 |
| --- | --- | --- |
| 기획·문구: **Haiku 5.5** | 짧은 한국어, 설명 길이, 과학/판타지 문구 확인 | 근거가 있는 문구 문제 최대 3개 |
| 구현·시각 검토: **Sonnet 5.5** | 모델·재질·게임 연결, 시안과 렌더의 차이 | 작은 제작 단위, 전후 화면 비교, 검사 대상 |
| 복잡한 통합: **Opus 5.5** | 모델 계층·좌표·애니메이션 계약, 여러 세션 충돌, 입력·저장·보상 불변식 | 확인된 위험, 해결 우선순위, 반례·회귀 조건 |
| 독립 QA 세션 | 변경 규모에 맞는 브라우저·엔진 검증 | 실패 재현 또는 통과 증거와 미검증 범위 |

매 주기 모든 모델을 호출하지 않는다. 작업 난도에 맞는 역할만 선택하고, 이미 확보한 검토로 해결되면 중복 호출하지 않는다. 공식 API에서 사용할 수 있는 모델과 실제 응답 모델을 확인한다. 요청한 5.5를 쓸 수 없으면 실패 원인을 기록하고 다른 버전으로 조용히 대체하지 않는다. 검토 답변은 코드·화면과 대조해 채택/기각하며 권위 있는 사실로 그대로 옮기지 않는다.

API 키 값은 출력하거나 문서·커밋에 넣지 않는다. 모델명, 요청/응답 ID, 사용량, 시간, 대상 파일 해시를 증거 폴더에 남긴다. 이미지 비전 검토를 실제 영상 생성이나 3D 모델 제작으로 표현하지 않는다.

## 검증과 증거

- 기준 화면과 수정 화면은 같은 뷰포트·스테이지·난이도·준비 상태로 비교한다. 현재 가용 기준은 모바일 세로 360×740 또는 390×844, 가로 844×390, PC 1440×900이다. 터치 목표·200% 글자·화면 회전·모션 줄이기는 영향을 받는 변경에서 확인한다.
- 브라우저에서 실제로 진입 → 선택/건설 → 시작 → 정지/복귀 → 결과의 관련 구간을 조작하고 상태 변화를 확인한다. 페이지 오류·실패한 에셋·잘림·빈 화면도 확인한다. 뷰포트 에뮬레이션은 실기기 검증과 구분한다.
- 로직 변경은 해당 엔진·저장·입력 회귀 테스트를, 통합 변경은 일반 테스트와 빌드를 실행한다. 카드 모드를 바꿨을 때에는 그 모드의 시뮬레이션·브라우저 검사도 실행한다. 통과 후 변경이나 새 우려가 없으면 동일 검사를 반복해서 시간을 쓰지 않는다.
- 성 외형은 경로·판정·피해·기존 저장을 바꾸지 않는지 확인한다. 완료 프레임과 보상 변경은 승리/패배 결과가 표시되고 보상이 한 번만 지급되는지 확인한다.
- 모델링 변경은 GLB·스프라이트 파일 용량, 가능하면 내보낸 메시·삼각형 수, 렌더·내보내기 설정과 실행 결과를 전후 기록한다. 모델실에서 로드·회전·공격 미리보기를, 전투에서는 투명 경계·잘림·접지점·방향·공격 모션을 확인한다. 모델실 수치만으로 전투 로딩·디코딩·프레임 비용이 줄었다고 판단하지 않는다.
- 성능은 동일 장면의 전후 수치로 비교한다. 실제 장치와 렌더러, 오브젝트/그리기 호출/메모리 등 측정 대상을 함께 적는다. 소프트웨어 렌더러의 FPS를 휴대폰 성능으로 해석하지 않는다.

로그·스크린샷·임시 검사 스크립트·API 영수증은 저장소 밖의 주기별 증거 폴더에 둔다. 권장 위치는 `/workspace/.cloud-setup/evidence/arcana-loop-YYYYMMDD-HHMM/`이며 이름은 KST 시작 시각 기준이다. 지속적으로 쓸 기획 결정과 채택된 변경 설명만 저장소 문서에 반영한다.

각 주기 결과에는 다음을 남긴다: 시작/종료 시각과 상태, 기준/최종 커밋, 다른 세션 변경, 선택한 문제와 이유, 구현 또는 무변경 이유, 검증 명령과 전후 화면 증거 경로, 관련 에셋 용량·지오메트리 지표, 채택/기각한 검토, 남은 위험, 다음 그래픽·모델링 후보 3개. 예약 자체가 실행됐는지와 개발 결과를 구분한다.

## 원격 반영

이 대화에서 사용자가 요청한 원격 병합과 그 범위의 후속 개발은 검증 후 원격 반영까지 이어간다. 이미 부여된 범위의 승인을 매 주기 다시 묻지 않는다. 다른 세션의 커밋·브랜치·미커밋 작업을 보존하고, 필요하면 별도 브랜치나 worktree에서 통합한다. 원격이 갱신되면 최신 변경을 읽고 합친 최종 상태를 검증한다.

PR을 사용하면 완성된 변경·테스트·한계를 설명하고 해당 PR을 작업에 첨부한다. 승인된 병합 범위이면 검사 후 병합·푸시·원격 커밋 확인까지 마친다. 범위를 크게 바꾸거나 검증이 끝나지 않은 작업은 검토 가능한 초안 PR로 남긴다. 충돌은 양쪽 의도를 보존해 해결하고, 강제 푸시·공유 브랜치 삭제·관련 없는 대량 변경으로 정리하지 않는다. 최종 통합 PR의 head SHA와 검증한 기준 SHA를 기록하고, 해당 diff를 작성자와 다른 검토자가 확인한다. 병합 직전에 원격 main을 다시 읽고 변경됐으면 관련 검증·검토를 갱신한다. API의 예상 head SHA 조건으로 검증한 커밋만 병합하며, mergeable 상태와 저장소의 필수 검사 조건을 확인하지 못하면 초안으로 남긴다. 코드 병합과 실제 서비스 배포는 별도 상태로 보고한다.

## 현재 클라우드 실행기

현재 연결에는 Codex 정기 작업 등록 API가 없다. 이 저장소의 `tools/arcana_loop.py`는 **클라우드 환경이 실행 중인 동안** 동작하는 로컬 실행기다. 환경이 정지·종료되면 실행도 멈춘다. 이 실행기가 환경을 다시 켜거나 앱에 다음 대화를 자동으로 생성하지는 않는다. GitHub Actions 기반 상시 예약은 등록하지 않았다.

실행기는 Linux의 프로세스 잠금·`/proc`, Python 표준 라이브러리와 Claude Code 2.1.312를 사용한다. Claude Code는 공식 API의 KR2 인증을 자식 프로세스에만 전달받고 Sonnet 5.5로 진행한다. 사용자·프로젝트 설정, 훅·메모리·스킬 자동 사용과 외부 MCP 연결을 제외하고 필요한 파일·명령·Agent 도구만 켠다. `--bare`는 Agent 도구도 숨기므로 역할 위임을 위해 사용하지 않는다. 역할별 모델 설정은 `tools/arcana_loop_agents.json`, 실제 반복 지시는 `tools/arcana_loop_prompt.md`다. 검증한 실행기·프롬프트·역할 설정은 `/workspace/.cloud-setup/arcana-loop/runtime/`에 복사해 사용한다. 다른 대화에서 저장소의 브랜치를 바꿔도 실행 중인 루프의 지시 파일이 사라지지 않게 하기 위한 고정본이다. 새 버전을 적용할 때는 루프를 중지하고 세 파일을 함께 교체한 다음 다시 시작한다. 현재 대화의 작업 폴더와 충돌하지 않도록 `/workspace/.cloud-setup/arcana-loop/workspace/edu_arcade_game_1`의 별도 Git 복사본과 나란한 `math_speed` 의존성을 사용한다.

환경 내 설정 파일은 `/workspace/.cloud-setup/arcana-loop/config.json`이다. 키 값을 포함하지 않는다. 기본값은 1시간 간격, 주기당 최대 50분·리드 64턴(마지막 12턴은 검증·독립 검토·전달용)이며 Claude CLI의 비용 한도는 주기당 8 USD다. 실제 사용량과 비용은 각 주기의 CLI 결과에서 확인한다. 예시는 `tools/arcana_loop.example.json`에 있다. 시간 초과·모델 오류는 실패로 기록하고 다음 주기에 무한 재시도하지 않는다.

```bash
# 상태와 다음 예정 시각
python3 /workspace/.cloud-setup/arcana-loop/runtime/arcana_loop.py status

# 실행 중인 환경에서 1시간 간격 루프 시작 (중복 시작 방지)
python3 /workspace/.cloud-setup/arcana-loop/runtime/arcana_loop.py start --config /workspace/.cloud-setup/arcana-loop/config.json

# 즉시 한 주기만 실행
python3 /workspace/.cloud-setup/arcana-loop/runtime/arcana_loop.py run-once --config /workspace/.cloud-setup/arcana-loop/config.json

# 루프와 이 실행기가 시작한 현재 작업 중지
python3 /workspace/.cloud-setup/arcana-loop/runtime/arcana_loop.py stop
```

상태와 주기별 결과는 `/workspace/.cloud-setup/arcana-loop/`에 남는다. 원자적 상태 기록과 프로세스 잠금으로 같은 루프의 중복 실행을 막으며, 중지되었던 주기를 몰아서 실행하지 않는다. 예약 프로세스가 살아 있다는 것과 각 개발 주기가 성공했다는 것은 다른 상태이므로 둘 다 확인한다. 첫 실행 전 API·도구 호출과 통제된 기준 점검을 시험한다. 실행기만 비정상 종료되고 이전 작업이 살아 있으면 `blocker`를 표시하고 새 작업을 시작하지 않는다. 이 경우 소유권을 확인해야 하며 오래된 PID 기록만으로 프로세스를 종료하지 않는다.

환경을 새로 만들었을 때는 Claude Code를 아래 명령으로 설치하고, 별도 작업 복사본과 설정 경로를 먼저 복구한다. 기존 미커밋 작업이나 주기 기록을 덮어쓰지 않는다. API는 환경의 준비된 KR2 바인딩을 사용하며 키를 새 파일에 복사하지 않는다.
